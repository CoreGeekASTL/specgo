## 填写说明

1. **章节顺序不可调换**：架构变更在前，Clean Code 在后，结论收尾。
2. **文档头部无元信息表格**：不写"检查对象/检查依据/检查范围"表，标题下直接进入章节一。
3. **合规项说明列写证据不写套话**：给出量化证据（最长函数行数、最高圈复杂度、常量名清单），禁止"命名良好""结构清晰"式空话；量化证据随整改刷新（如修复后函数行数变化，写修复后数值）。
4. **规范编号规则**：通用规则用数字编号（如 `13`），语言特则用语言前缀编号（如 `G3`、`J2`）；同一表格可混排。
5. **提示/豁免项判定依据必须可追溯**：语言惯例冲突写明冲突双方（如"gofmt 强制 tab vs 规范 4 空格"）；刻意设计写明业务依据；存量延续写明"延续但未新增重复"。
6. **违规项章节去留（由"报告问题并询问"的用户选择决定）**：用户选择"不修复"时保留 2.2 违规项章节原文交付（含位置/问题/建议修复方式）；用户选择"修复"且回归通过后删除 2.2，违规条目并入 2.1（说明列写明修复后形态，如"字面量均已常量化：`csvFieldCount`"），量化证据刷新为修复后数值，验证结果表记录整改后回归结果。禁止修复后仍保留过期的违规描述。
7. **mermaid 图配色固定**：新增 `#d4edda/#28a745`、织入 `#fff3cd/#fd7e14`；织入边用 `== "标签" ==>` 加粗实线；图下必须带图例行。
8. **架构维度表八行固定**：分层架构/对外接口/数据表/关键数据结构/既有代码织入方式/新增依赖/可用性策略/并发模型，无该维度变更的写"无变更"不删行。
