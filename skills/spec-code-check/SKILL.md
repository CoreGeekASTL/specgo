# 需求代码检查（clean code + 架构变更）

在需求代码实现完成后、资产刷新（spec-asset-refresh）前执行，回答两个问题：**"这次需求改的代码符不符合整洁规范"** 和 **"这次需求给架构带来了什么变更"**，产出一篇检查文档归档到 `docs/engineering/code-check/{需求名}代码检查.md`。

> 定位：本 skill 是"代码实现完成 → 资产刷新"之间的质量闸门。检查对象是**需求 commit 的增量代码**，不是全仓扫描；架构结论以 `docs/` 下已产出的资产（interface/story/data-structure/key-class/structure）为比对基线。

分析遵循五步工作流：

1. 明确检查对象与依据
2. 读取变更代码（新文件全量 + 修改文件看 diff 增量）
3. 架构变更分析
4. Clean Code 逐项检查
5. 报告问题并询问是否修复 → 按用户选择产出对应形态文档 + 渲染验证 +（选"是"时）整改后回归验证

## 第 1 步：明确检查对象与依据

- **检查对象**：需求实现的 commit（用户给定 hash，或当前分支相对基线的 diff）。用 `git show --stat <commit>` 确定变更文件清单与新增行数。**用户未给定 commit 时**：需求跨多个 commit 用 `git diff <基线>..HEAD --stat` 合并视图；只有未提交改动时用 `git diff`/`git status` 确定范围；无法确定基线时向用户确认，禁止臆造检查范围。
- **检查依据**：默认使用内置规则 [references/clean-code-rules.md](references/clean-code-rules.md)（**通用 27 条 + 语言特则**，含语言惯例冲突的默认豁免判定与高发违规区提示）。**用户给定外部规范文档时，以用户文档为准**（作为内置规则的覆盖或补充）；内置规则已覆盖常见 clean code 维度，用户不给定规范属正常路径，直接使用内置规则，无需询问。
- **语言确认**：确认仓内主语言（Go/Java/Python/C++），据此启用规则文件中对应的语言特则章节（G/J/P/C 编号）；多语言仓按文件归属分别覆盖，其它语言特则章节跳过。
- **架构比对基线**：`docs/` 下既有资产（interface/story/data-structure/key-class/structure），用于判定"架构变了什么、资产是否同步"。
- **范围红线**：只检查需求新增/修改的代码行，**存量未改动行不纳入问题统计**；修改文件先用 `git show <commit> -- <file>` 确认增量行，避免把存量问题算到本需求头上。

## 第 2 步：读取变更代码

- 新增文件全量读取；修改文件读取全文但只对 diff 增量部分做问题判定。
- 同时读取被变更代码依赖的上下文（接口定义、基类、常量定义），确保检查结论有依据（如返回值语义、错误码约定）。
- 测试文件同样纳入检查（测试命名、断言中的魔法数字可放宽判定，见第 4 步豁免规则）。

## 第 3 步：架构变更分析

从八个维度比对"实现前 → 实现后"，逐维度给出 ✅/⚠️/❌ 评估：

| 维度 | 检查点 |
| --- | --- |
| 分层架构 | 新代码是否落在既有分层（如 Controller→Service→DAO→Model），有无跨层调用/层级破坏 |
| 对外接口 | 新增/变更的接口（路由/RPC/消息），注册在内部还是外部入口，是否已沉淀接口文档；**既有接口的契约/行为是否被改变**（新增前置拦截、出入参变化、错误码变化），对调用方的影响是否评估并注明 |
| 数据表 | 新增/变更的表与索引，多数据源/多方言 DDL 是否同步（如 MySQL/SQLite 双写一致） |
| 关键数据结构 | 新增的自定义容器/缓存/队列等，是否已沉淀数据结构文档，有无并发隐患（无锁裸 map 等） |
| 既有代码织入方式 | 横切逻辑（鉴权/限流/日志）以何种方式织入既有链路（代码注入 vs 框架 Filter/拦截器），有无漏织入风险与重复注入 |
| 新增依赖 | 模块间新增依赖方向（如 Service→Service 横向依赖），是否单向无环 |
| 可用性/安全策略 | 引入的架构级取舍（逃生态、fail-open、降级），决策是否显式（注释+日志），运维影响是否需知悉；**敏感信息保护**：新增日志禁止输出密码/密钥/token/连接串，新增代码禁止硬编码密钥 |
| 并发模型 | 锁保护/goroutine 模型是否清晰，与仓内既有并发隐患模式（见 data-structure 资产全局风险）有无重蹈 |

另需核对**架构资产同步状态**：对照 `docs/biz/interface/`、`docs/business/story/`、`docs/business/data-structure/`、`docs/business/key-class/`、`docs/arch/structure-model/`，逐类标注"已同步 / 缺口（缺什么）"。缺口写入检查文档，供后续 spec-asset-refresh 处理。

**架构变更图硬性要求**：

- 必须产出一张 mermaid flowchart，**用颜色一眼区分变更点**：
  - 绿色节点（`classDef newNode fill:#d4edda,stroke:#28a745`）= 本次新增组件
  - 橙色节点（`classDef wovenNode fill:#fff3cd,stroke:#fd7e14`）= 既有组件上的织入/修改点
  - 织入边用加粗实线 `== "标签" ==>`，与新增链路内部依赖边区分
  - 新增数据表用圆柱体 `[("表名")]`
- 图下方补一行图例说明颜色含义。
- 禁止全部节点同一色系、靠文字找变更点——渲染后必须"一眼看出改了哪里"。

## 第 4 步：Clean Code 逐项检查

按第 1 步确认的检查依据（内置规则或用户给定文档）**逐条过**——通用 27 条全量覆盖 + 按仓内主语言覆盖对应语言特则章节（引用格式 `G3`、`J2`），每条给出 ✅ 合规 / ⚠️ 提示 / ❌ 违规及证据（`文件:行号`）。规则原文、语言惯例冲突的默认豁免判定表、高发违规区清单均见 [references/clean-code-rules.md](references/clean-code-rules.md)。检查结果分三类呈现：

1. **合规项**：无问题的条目，表格列出（#/规范/结论/说明），说明中给出关键证据（如"最长函数 X 38 行"）。
2. **违规项**：必须修复的条目，表格列出（#/规范/位置/问题/建议修复方式）。
3. **提示 / 豁免说明项**：以下三种情形不判违规，但**必须写明判定依据**，禁止静默放过：
   - **规范与语言/框架惯例冲突**（如 Go gofmt 强制 tab vs 规则 #7"4 空格缩进"、Go testing 强制 `Test` 前缀 vs 规则 #27 `should..._When...`）→ 判"豁免"，遵循语言惯例与仓库存量风格。内置规则的默认豁免判定表见 [references/clean-code-rules.md](references/clean-code-rules.md)，表外冲突情形按同一原则判定并写明依据。
   - **刻意设计决策**（如调用方刻意忽略某返回值、read-through 缓存的查询带写副作用）→ 判"刻意设计/豁免"，并要求代码中补注释说明取舍。
   - **存量问题延续**（如本需求在存量重复代码块中同步注入相同逻辑）→ 判"提示"，注明"延续但未新增重复"，不列为本需求违规。

检查要点：优先核对内置规则文件「高发违规区」六类（布尔命名缺前缀/魔法数字/DRY 多副本/SLAP 混层/模糊缩写/忽略返回值无注释），再覆盖其余条目，禁止只查高发区就交付。

## 第 5 步：报告问题、询问分流、产出文档 + 验证

### 5.1 报告检查结果并询问用户是否修复（强制交互，不可跳过）

第 3、4 步检查完成后、产出文档前，**必须先把检查发现的问题报告给用户，并询问是否修复**：

1. **报告问题**：在回复中列出检查结果摘要——架构变更要点、违规项清单（#/规范/位置/问题/建议修复方式，逐条列出）、提示豁免项要点。无违规项时明确说"未发现违规项"。
2. **询问分流**：有违规项时，必须用询问工具（question/ask-human）让用户选择：
   - **修复**：进入 5.2 修复与回归验证，完成后按 5.3 产出"修复后文档"（违规项并入合规项）。
   - **不修复**：跳过修复，按 5.3 产出"修复前文档"（保留违规项章节，含建议修复方式）。
3. **禁止行为**：禁止不报告不询问直接修复；禁止不询问直接按"不修复"出文档；无违规项时无需询问，直接产出文档。

### 5.2（用户选择"修复"时）修复与回归验证

1. 按违规项逐项修复；修复范围仅限本需求新增/修改的代码，不顺手改存量。
2. 修复后必须回归验证（按仓库可用命令，缺啥补啥）：
   - 编译（如 `go build`）+ 静态检查（如 `go vet`）；vet 报错区分存量/新增，存量问题注明不背锅。
   - 单元测试（如 `go test ./<改动包>/...`）。
   - **集成测试（仓内存在集成/E2E 测试约定时必跑，不可等用户提醒）**：按仓内既有方式启动本地环境，全量跑需求相关用例，全部通过；跑完停服务、清理测试数据。
   - **测试造假红线**：回归失败时必须回到代码修复，禁止通过修改测试断言/看护点、删除用例来让测试"通过"。
3. 回归通过后按 5.3 产出"修复后文档"，再交付。

### 5.3 产出检查文档（两种形态）

输出**一篇** `docs/engineering/code-check/{需求名}代码检查.md`，章节结构固定如下，模板见 [references/report-template.md](references/report-template.md)：

```
# {需求名} 需求代码检查报告
## 一、架构变更检查        # 在前：mermaid 变更图（颜色区分） + 八维度评估表 + 资产同步状态表
## 二、Clean Code 逐项检查  # 在后：合规项 / 违规项（仅未整改时保留）/ 提示豁免项 / 修改文件专项检查
## 三、结论与验证          # 结论（通过/有改进项） + 验证结果表
```

**两种产出形态**（由 5.1 用户选择决定）：

- **修复前文档**（用户选择"不修复"）：保留「2.2 违规项」章节原文（含位置/问题/建议修复方式），验证结果表只记录检查期的编译/测试现状。
- **修复后文档**（用户选择"修复"，且 5.2 回归通过）：删除「2.2 违规项」章节，违规条目并入「2.1 合规项」（写明修复后形态，如"字面量均已常量化：`csvFieldCount`"），量化证据（函数行数/圈复杂度）同步刷新为修复后数值，验证结果表记录整改后的回归结果；禁止修复后仍保留过期的违规描述。

硬性要求：

- **架构变更章节在前，Clean Code 在后**——评审者先看清"架构变了什么"，再看"代码是否整洁"。
- **文档头部不放元信息表格**（检查对象/依据/范围表），直接从标题进入章节。
- 检查范围说明（commit、依据、新增行数）不写入文档正文，在交付回复中说明即可。
- 规范编号：通用规则用数字编号（如 `13`），语言特则用语言前缀编号（如 `G3`、`J2`），安全附加项用 `S1~S3`。
- mermaid 图必须本地验证 VALID（见 5.4）。

### 5.4 验证 mermaid 图可渲染

```bash
node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <检查文档路径>
```

全部 VALID 才算完成；INVALID 按报错行号修复后重验。画图规则见 spec-mermaid-diagram skill 的「语法红线」。

## 质量检查清单

交付前逐项确认：

- [ ] 检查对象为本需求 commit 增量代码，存量未改动行未计入问题
- [ ] 通用 27 条 + 仓内主语言对应的语言特则章节 + 安全附加项 S1~S3 均已逐条覆盖（每条有结论，多语言仓按文件归属分别覆盖）
- [ ] 每条规范都有结论（合规/违规/提示豁免），提示豁免项写明判定依据，无静默放过
- [ ] **已先向用户报告问题清单并询问是否修复，按用户选择走了对应路径（修复 → 5.2 回归 → 修复后文档 / 不修复 → 修复前文档）**；无违规项时未做多余询问
- [ ] 架构变更覆盖八个维度（分层/接口/数据表/数据结构/织入方式/依赖/可用性策略/并发模型）
- [ ] mermaid 变更图用绿色=新增、橙色=既有织入、加粗边=织入边，图例齐全，渲染后一眼可辨变更点
- [ ] 架构资产同步状态已逐类核对（interface/story/data-structure/key-class/structure），缺口已列出
- [ ] 文档归档 `docs/engineering/code-check/{需求名}代码检查.md`，章节顺序：架构变更 → Clean Code → 结论与验证
- [ ] 文档头部无元信息表格；违规项章节按用户选择去留（未修复保留 / 修复后并入合规项），无过期违规描述
- [ ] mermaid 图已通过 validate-mermaid.mjs 验证全部 VALID
- [ ]（若修复）修复仅限本需求增量代码；build/vet/单测/E2E 回归全部通过并写入验证结果表；未改测试断言凑通过
