# 代码对照读取范围纪律（spec-requirement-audit 阶段 2 用）

代码对照的目的是核实**文档涉及的存量事实**，不是做全仓分析。读取范围必须收敛，防止把需求审核变成代码走查。

## 读取范围

只读与需求文档**直接点名或直接涉及**的代码：

| 需求中出现的线索 | 对应要读的代码 |
| --- | --- |
| 点名的接口 / 路由 / 消息 | 该接口的 Controller 方法、路由注册行、请求响应结构 |
| 点名的既有功能 / 流程（将被注入或变更） | 该链路的主干文件（service 入口 + 被注入函数） |
| 点名的规则 / 校验 / 状态机 | 规则所在函数与分支 |
| 点名的表 / 缓存结构 | 对应 model / dao 文件 |
| 点名的外部调用 | 调用点函数 |

## 查找方式

1. 用文档中的标识符（接口名、函数名、表名、术语英文映射）做 grep/glob 定位，命中后只打开命中文件的相关函数级片段。
2. 术语与代码命名的映射不确定时，优先查 `docs/0-biz/lexicon/`（存在时）；仍不确定的标「待确认」进断点清单，**不猜**。
3. 单个需求的对照读取一般不超过 10 个文件；超过时停下来，把"文档涉及面过大"本身作为断点交用户裁剪范围。

## 禁止事项

- 禁止全仓通读、禁止列目录漫游式阅读。
- 禁止评估与需求无关的代码质量/设计问题（那是 asset-audit 与各 analyze 子流程的职责）。
- 禁止修改任何代码文件——代码对照只读。

## 输出口径

对照结果三类去向：

1. **不一致 / 不存在** → 断点清单（类别「文档与代码不符」），附代码证据（文件路径 + 函数名，不带行号）。
2. **注入点 / 复用点** → 审核报告「代码对照结论」节（文件路径 + 函数名）。
3. **一致** → 报告中一句话带过（"文档 §x.x 描述与 `<文件>` 现状一致"），不展开。
