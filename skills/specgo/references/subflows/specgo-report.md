# specgo-report — 需求到代码全链路分析报告

代码生成收口后的报告生成 skill。让人一眼看出：**改了什么、每处改动对应哪条业务规则、引用的资产靠不靠谱**。

## 报告结构（固定三节）

| 节 | 内容 | 事实来源 |
| --- | --- | --- |
| 一、测试用例执行结果 | DT 到测试函数级、集成到用例步骤级，含验证命令与环境前置 | 验证命令实跑输出 |
| 二、代码修改清单 | 文件 × 函数粒度一览表，**含「业务规则」列** | `git diff` |
| 三、变更框图与引用资产质量评估 | mermaid 变更框图串联修改逻辑 + 逐变更推理（变更内容 + 引用文档四列表格） | story/develop-task 引用 + 实现期实际加载文档清单 |

## 何时触发

- specgo 全链路第 6 步调度（主流程收口，主要路径）。
- 用户单独要求对某需求补出/重出全链路分析报告："生成交付报告"、"重出报告"、"specgo-report"。

## 输入

| 输入 | 来源 | 缺省处理 |
| --- | --- | --- |
| story 设计文档 + develop-task | 被分析仓 `docs/1-storys/{功能名}/` | 缺失则停止并提示先跑 spec-story-design |
| 测试执行事实 | 调度方（specgo 第 4 步）返回的 DT/集成结果；单独触发时由本 skill 复跑验证命令取证 | 禁止凭"已通过"印象填写 |
| 代码变更 | `git diff`（已提交取本次需求 commit 范围，未提交取工作区） | 唯一事实来源 |
| 业务规则清单 | story「业务规则」要素章节 + `docs/0-biz/rules/` 相关规则条目 + develop-task 澄清裁定 | 三方合并去重 |
| 引用资产清单 | story「外部文档引用」+ develop-task 框架表 + 实现期实际加载文档清单 | 逐条去重合并 |

## 工作流程

### 第 1 步：取证（禁止凭印象）

1. **测试用例执行结果**：收集验证命令实跑输出；证据不足时复跑验证命令补证。DT 到测试函数级（逐函数 PASS/FAIL + 看护点），集成到用例步骤级（逐步骤结果 + 环境前置——数据基线/服务依赖/环境变量）。
2. **代码修改清单**：以 `git diff` 为唯一事实来源，逐文件核对 develop-task 修改文件清单——清单外改动、清单内未改都要显式暴露。
3. **业务规则清单**：从 story 业务规则章节、`docs/0-biz/rules/rules-*.md` 相关条目、develop-task 澄清裁定三方提取合并，作为第二、三节的**共同主键**。
4. **引用资产清单**：story「外部文档引用」+ develop-task 框架表 + 实现子代理返回的实际加载文档清单，去重合并。
5. 冲突偏差与待确认事项收集为评估依据，不单独成节。

### 第 2 步：按模板撰写三节报告

按 ../assets/report--report-template.md 填充：

1. **测试用例执行结果**：失败用例必须列出并附处理结论；前置不满足导致的失败显式标注。
2. **代码修改清单**：表格四列——文件 / 新增或修改函数 / 变更说明（≤30 字）/ **业务规则**（该改动实现或对齐的规则条目；测试代码填其看护的规则；清单外改动与产物填「清单外（无规则）」）。
3. **变更框图与引用资产质量评估**：先用一张 mermaid flowchart 把本次代码修改逻辑串联成变更框图（按调用链路布点，变更节点标注"变更：xxx"并统一配色）；图下针对图中每一处变更给推理——变更内容一行 + **引用文档四列表格**（引用文档 / 应用了文档中的什么内容（≤30 字）/ 文档质量评分（符合/部分符合/不符合）/ 文档优化建议）+ 结论一行；推理所引文档与第二节「业务规则」列同口径可追溯，重点呈现**缺引用**（无资产支撑、全靠读代码反推）与**质量不足**（评分低于"符合"），优化建议列必须指回具体 skill 重跑或文档修订；节末汇总缺引用与质量不足清单；附注未引用但发现失实的资产问题。

### 第 3 步：落盘与收尾

- 落盘被分析仓 `docs/1-storys/{功能名}/{YYYYMMDD}-report.md`（与本需求 story/develop-task 同目录；次抛件带日期，同日同需求重跑同名覆盖）。
- 含 ```mermaid 代码块时，用 mermaid-validate 的 validate-mermaid.mjs 逐文件校验全部 VALID 后才算完成。
- 评估为「部分符合/不符合」的资产，在返回中显式列出并给下一步建议（如重跑某 analyze skill、补齐某资产后再生成）。

## 输出模板

- ../assets/report--report-template.md（元信息 + 三节固定结构）。

## 关键约束

- **基于实证**：测试结果/修改清单/引用资产评估必须以实跑输出、git diff 与各步骤返回事实取证，逐用例逐文件逐篇落实，禁止臆造。
- **两表同口径**：第二节「业务规则」列与第三节主键必须同一份规则清单——规则命名一致、全覆盖、无孤儿行（清单里出现的规则评估表必有行，评估表的规则在清单里能追到代码或显式注明无代码变更）。
- **规则可追溯**：业务规则条目优先引用 `docs/0-biz/rules/` 既有条目名；story/裁定新增的规则写清来源（如"2026-08-12 裁定"）。
- **清单外显式暴露**：清单外改动、清单内未改、非代码产物都要列入并标注「清单外」。
- **次抛带日期**：报告文件名带日期，同日同需求重跑同名覆盖；不改动 story/develop-task 本体。
- **文档语言**：输出报告用中文，技术术语（DT / E2E / fail-open / TTL 等）保留英文。
