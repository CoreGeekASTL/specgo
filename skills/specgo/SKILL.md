# specgo — 规格化全链路编排（主流程）+ 链路子流程路由

新功能从需求到交付的唯一编排入口。主代理不亲自分析、设计、编码——只做流程推进、用户确认、子代理派发与验收。

**双重职责**：

- **编排模式**（默认）：用户要求端到端开发时，按六步流程串联各子流程；
- **单环节模式**：用户只请求某一环节（如"审核需求文档"、"按 story 生成代码"）时，按下方路由表读取对应子流程文件全文并严格按其执行，不强行串联前后步骤。

**路径锚定**：本文件中所有相对路径均以本 SKILL.md 所在目录为锚；派子代理时必须先把子流程文件解析成**绝对路径**写进 prompt，子代理不猜路径。

## 子流程路由表

| 子流程 | 触发意图 | 子流程文件（references/subflows/） |
| --- | --- | --- |
| spec-function-design-audit | 需求/功能设计审核、多彩建模、逻辑断点扫描、表述质量检查 | `spec-function-design-audit.md` |
| spec-story-design | 需求文档 → story + develop-task 设计 | `spec-story-design.md` |
| spec-code-generate | 按 story/develop-task 生成完整代码（零 TODO）与测试 | `spec-code-generate.md` |
| spec-update | git 变更驱动的 docs/ 资产增量刷新 | `spec-update.md` |
| specgo-report | 需求到代码全链路分析报告 | `specgo-report.md` |

子流程引用的模板/脚本在 `references/assets/`（`<环节短名>--<文件名>`）。

## 分工原则

| 角色 | 职责 |
|---|---|
| 主代理 | 步骤推进与衔接；所有与用户的询问/确认；派发子代理（prompt 含子流程文件绝对路径+输入+产出+返回要求）；验收子代理产出；每步末组织 ask-human 审视门；汇总报告 |
| 子代理 | 干活：资产分析、建模审核、story 撰写、代码实现与测试、代码检查与修复。每个子代理**第一步必须读取主代理给定的子流程文件全文**再开工 |

**用户交互中转模式**：子代理执行中遇到需要用户输入的点（断点补齐、疑问澄清、修复决策），不得自行脑补——返回"待确认清单"结束本轮；主代理向用户询问后，把答案回传**同一子代理**（task_id 续会话）继续，不新起子代理重做。

## 固定 ask-human 审视门（最高纪律）

**每个步骤的校验环节结束，固定进入 ask-human 审视门——无一例外：**

1. 主代理列出本步**新生成/修改的全部文档与代码清单**（逐条带路径），附验收结论（mermaid VALID 结果、测试/构建命令结果、待确认项闭环情况），用 AskUserQuestion 询问用户是否审视通过。
2. 用户审视通过 → 才允许进下一步；用户有意见 → 主代理把意见回传对应子代理（task_id 续会话）整改，整改后**重新过同一道门**。
3. 尤其任何**新生成文档**（资产文档、建模 HTML、story/develop-task、刷新后的资产文档、全链路分析报告）必须经人审视后才允许继续执行——子代理自验 VALID/通过不等于门通过，主代理验收通过也不等于门通过。
4. 不默认、不跳过、不替用户回答；用户明确要求"后面都别问了"时，在最终报告中注明被跳过的门。

## 第 1 步：资产检查与录入/刷新

1. 探测四类核心资产目录：`docs/` 下——`0-biz/interface/`、`0-tech/framework-guidelines/`、`0-tech/external-call-guidelines/`、`0-arch/structure-model/`（README.md 仓级总览 + structure-model-*.md）。
   - 需要全套 16 类资产（含 rules/object-model/data-model/lexicon 等）时，改派 spec-analyze 主 skill 做一键全量分析，本步后续小步跳过。
   - `docs/business/` 旧体系资产目录（story/key-class/data-structure 等）如存在仅作"外部文档引用"素材，不再探测录入（对应旧分析 skill 已删除）。
2. 分支：
   - **存在** → 询问用户是否需要刷新资产
   - **不存在** → 询问用户是否需要录入资产
   - **选否** → 跳过本步；后续步骤的"外部文档引用"章节按"无引用"处理
3. **选是** → 同一条消息**并行**派发 4 个子代理，每个读取 spec-analyze 下对应分析子流程文件全文后执行（可让用户勾选子集，默认全量）：
   - structure → `skills/spec-analyze/references/subflows/arch-structure-model-analyze.md`
   - interface → `skills/spec-analyze/references/subflows/biz-interface-analyze.md`
   - external-call-guidelines → `skills/spec-analyze/references/subflows/tech-external-call-guidelines-analyze.md`
   - framework-guidelines → `skills/spec-analyze/references/subflows/tech-framework-guidelines-analyze.md`
4. 验收：产出文档落位对应目录；含 mermaid 的文档全部通过 mermaid-validate 验证脚本（VALID）。
5. **审视门**：列出本步新生成/刷新的资产文档清单（带路径）+ VALID 结论，ask-human 审视通过后才进第 2 步。

> 注：交互模型文档（docs/0-arch/interaction-model/interaction-model-*.md）不属于本步自动检查的资产——它由用户主动指定流程后经 arch-interaction-model-analyze 子流程提取产出，不派全量子代理。

## 第 2 步：需求与功能审核（spec-function-design-audit）

- 派**审核子代理**：读取 `references/subflows/spec-function-design-audit.md` 全文执行（需求/功能设计审核），输入=需求/SR/功能设计文档，完成多彩建模翻译 + 全面扫描（表述质量/逻辑断点/设计要素）+ HTML 初版。
- 子代理返回合并断点清单；**主代理**批量抛出全部问题 ask-human（每问给 2-4 个候选答案+推荐项），用户批量回答后核对——未答/含糊/引入新疑点的继续批量追问，无新问题的答案回传子代理补齐，直至建模闭环、HTML 定稿。
- 审核通过后按子流程阶段 6 询问用户是否输出规范功能实现设计 md。
- **审视门**：建模闭环后，列出定稿 HTML（及可选的规范功能设计 md）路径，ask-human 审视通过后才进第 3 步。
- 用户明确说"需求已确认、不用审核"时可跳过，并在最终报告中注明。

## 第 3 步：story 设计（spec-story-design）

- 派**设计子代理**：读取 `references/subflows/spec-story-design.md` 全文，输入=第 2 步审核通过的 Spec + 第 1 步资产文档（framework-guidelines 框架指导 + docs/1-storys 既有 story 为参照）。
- 产出 `docs/1-storys/{功能名}/` story 目录：`{功能名}-story.md`（八类核心要素结构，标注新增/变更/不涉及）+ `{功能名}-develop-task.md`（同目录）。
- 子代理在 develop-task 第 5.2 步返回疑问清单 → 主代理批量向用户澄清 → 回传子代理定稿。
- 主代理验收：story 八类核心要素判定完整（变更条目写清更改对象与内容）、develop-task 修改文件清单到函数级、mermaid 全部 VALID。
- **审视门**：列出 story 与 develop-task 文档路径 + 验收结论，ask-human 审视设计，通过后才进第 4 步。

## 第 4 步：代码实现与测试（spec-code-generate 调度）

**先询问用户**：设计已完成，是否直接开始实现代码？选否 → 停在本步，输出阶段总结。

选是 → 读取 `references/subflows/spec-code-generate.md` 全文，按其角色分工执行：

- 铁律一：**完整代码零 TODO**——任何 TODO/占位符/省略式留空都是交付红线，写不出完整实现就返回待确认清单；
- 铁律二：**子代理只实现代码，可并行多个**——主代理评估实现规模，修改文件清单可拆为互不依赖的文件组时同一条消息并行派发多个实现子代理（按文件分组，组间有依赖严格串行）；测试代码由实现子代理一并编写；
- **主代理执行测试与后续流程**——子代理职责到"代码写完"为止；主代理组装产出、复核零 TODO（实跑搜索命中数=0）、实跑单测（到测试函数级）与集成/E2E 测试（到用例步骤级，仓内有就必须主动跑）、运行 develop-task 验证命令，失败打回实现子代理修复重跑。

汇总返回 spec-code-generate 规定的返回格式：生成/修改文件清单 + 冲突偏差 + 零 TODO 自检结果 + 验证命令结果（DT 到测试函数级）+ 集成测试结果（到用例步骤级）+ 实际加载的文档清单（供第 6 步报告取证）。

**审视门**：主代理汇总代码变更摘要（git diff 文件清单 + 函数级改动概述）、零 TODO 自检结果、单测/集成测试与验证命令结果，ask-human 审视代码实现，通过后才进第 5 步；有意见回传实现子代理整改后重新过门。

## 第 5 步：资产刷新（spec-update）

1. 前置：本需求代码变更已就绪。spec-update 以 git 对比为输入——代码已 commit 时基线最清晰；未 commit 也可基于工作区 diff 执行。**是否提交代码由用户决定，不得主动提交**。
2. 派**资产子代理**：读取 `references/subflows/spec-update.md` 全文，基于 diff 识别变更映射到各资产要素的受影响情况，产出刷新清单（受影响/不受影响/资产未建三态判定 + 依据）。
3. 子代理返回刷新清单；**主代理交用户审核确认（可勾选子集）后**，子代理按最新要素定义执行增量刷新、定稿落盘。
4. 含 mermaid 的刷新文档必须全部 VALID；资产文档有增删时按 spec-index 子流程（`skills/spec-admin/references/subflows/spec-index.md`）口径收口索引。
5. **审视门**：列出本步实际刷新的资产文档清单（带路径）+ VALID 结论，ask-human 审视通过后才进第 6 步。

## 第 6 步：全链路分析报告（specgo-report 调度，收尾必做）

代码生成收口后，调度 specgo-report 产出**需求 → 代码全链路分析报告**，让人一眼看出改了什么、每处改动对应哪条业务规则、引用的资产靠不靠谱。

1. **取证**（主代理汇总各步骤已返回的事实，禁止凭印象）：
   - 测试用例执行结果：第 4 步返回的 DT（测试函数级）与集成（用例步骤级）结果 + 验证命令实跑输出；证据不足时主代理复跑验证命令补证；
   - 业务规则清单：story 业务规则章节 + docs/0-biz/rules/ 相关条目 + develop-task 澄清裁定，三方合并（第二、三节共同主键）；
   - 代码修改清单：以 `git diff`（已提交则取本次需求 commit 范围）为唯一事实来源，逐文件核对 develop-task 修改文件清单——清单外改动、清单内未改都要显式暴露；
   - 引用资产清单：story「外部文档引用」章节 + develop-task 框架表 + 第 4 步实现子代理返回的实际加载文档清单，逐条去重合并；
   - 各步骤返回的冲突偏差、待确认事项（作为资产评估依据，不单独成节）。
2. **派报告子代理**：读取 `references/subflows/specgo-report.md` 全文（prompt 含上述取证材料），按其三节模板产出报告——测试用例执行结果 / 代码修改清单（含「业务规则」列）/ 引用资产质量评估（业务规则主键，与修改清单同口径）。
3. **落盘**：被分析仓 `docs/1-storys/{功能名}/{YYYYMMDD}-report.md`（归档进本需求的 story 目录，与 story/develop-task 同目录；次抛件带日期，同日同需求重跑同名覆盖）。
4. **审视门**：报告落盘后，ask-human 审视报告全文；有意见回传报告子代理修订后重新过门，审视通过后流程结束。
5. 评估为「部分符合/不符合」的资产，主代理在回复中显式列出并给出下一步建议（如重跑某分析子流程、补齐某资产后再生成）。

## 子代理派发通用规则

- prompt 四要素：①子流程文件绝对路径（先读全文再开工）②输入文档/数据路径 ③产出路径与格式 ④返回内容（产出文件清单 + 关键结论 + 待确认清单 + 阻塞项）。
- 无依赖的子代理同一条消息并行派发（第 1 步 4 个分析、第 5 步各资产刷新）；步骤间有依赖严格串行。
- 主代理验收不过关就打回子代理整改，不亲自代写。

## 确认门总表

| 节点 | 询问内容 |
|---|---|
| 第 1 步 | 资产存在→是否刷新；不存在→是否录入（可选子集）；**末：新生成/刷新的资产文档 ask-human 审视门** |
| 第 2 步 | 断点批量 ask-human；审核后是否输出规范设计 md；**末：建模 HTML/设计 md ask-human 审视门** |
| 第 3 步末 | **story + develop-task 设计文档 ask-human 审视门** |
| 第 4 步前 | 是否直接开始实现代码 |
| 第 4 步中 | 需求未明确处澄清（子代理返回待确认清单时） |
| 第 4 步末 | **代码变更 + 测试结果 ask-human 审视门** |
| 第 5 步 | 资产刷新清单审核确认（可勾选子集）；代码是否提交由用户决定；**末：刷新后的资产文档 ask-human 审视门** |
| 第 6 步末 | **全链路分析报告 ask-human 审视门**——审视通过后流程结束 |

## 红线

| 想法 | 现实 |
|---|---|
| "步骤简单，我主代理顺手做了" | 分析/设计/编码/检查一律派子代理，主代理只编排与确认 |
| "这个断点/疑问我补个合理答案" | 所有需求疑问走待确认清单→主代理问用户，不脑补 |
| "设计和代码并行跑省时间" | 步骤间严格串行，确认门不过不进下一步 |
| "文档生成了，VALID 也过了，直接进下一步" | 每步校验环节结束固定过 ask-human 审视门——VALID/测试通过只是门的输入，人审视通过才算过门 |
| "代码都测过了，不用再给人看" | 第 4 步末代码变更必须列 diff 摘要 + 测试结果交人审视，通过后才进资产刷新 |
| "报告是收尾交付物，落盘即结束" | 第 6 步报告同样过 ask-human 审视门，审视通过流程才结束 |
| "集成测试等用户提醒再跑" | 仓里有集成/E2E 测试就必须主动运行 |
| "代码写完直接交付" | 第 5 步资产刷新是收口闸门，docs 不同步需求不算完成 |
| "分析报告凭印象总结一下" | 第 6 步报告的测试结果/修改清单/引用资产评估必须以实跑输出、各步骤返回与 git diff 取证，逐用例逐文件逐篇落实，禁止臆造 |
| "commit 一下方便做 diff" | commit 必须用户明确同意 |
| "子流程让子代理用 Skill 工具加载" | 子流程不是独立 skill，必须把文件绝对路径写进 prompt 让子代理读取 |

## 与其它 skill 的关系

本 skill 承载 5 个链路子流程（路由表见上），六步编排额外调用：spec-analyze 的 4 个分析子流程（第 1 步；全套 16 类资产录入改用 spec-analyze 全量模式）、mermaid-validate（贯穿各步的图验证）。各子流程也可脱离编排单独触发（单环节模式或对应 `/` 命令）。
