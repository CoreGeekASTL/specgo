# specgo — 文档驱动代码生成

只读指定设计文档、它显式引用的仓内文档、以及 `docs/develop-task/` 下同名关联的代码生成任务文档，直接生成代码。不做需求分析、不做设计、不自主探索代码仓——这些已由上游 spec skill 完成并沉淀在文档里。

## 文档命名关联（核心约定）

| 文档 | 路径 | 角色 |
|---|---|---|
| story 设计文档 | `docs/story/feature-<功能名>.md` | 业务逻辑、接口、数据结构、时序、AI 编码指南的依据 |
| 代码生成任务文档 | `docs/develop-task/<功能名>-develop-task.md` | 修改文件清单（编码的唯一任务来源）+ 验证方式 |

两个文档通过 `<功能名>` 互相推导：`feature-<功能名>.md` 去掉 `feature-` 前缀、加上 `-develop-task` 后缀；反向同理。

## 工作流（顺序执行）

### 第 1 步：定位输入文档

用户输入三种形态，都归一到同一对文档：

1. **story 文档路径**（如 `docs/story/feature-terminal-auth.md`）→ 推导 develop-task 路径
2. **develop-task 文档路径** → 反推 story 文档路径
3. **功能名**（如 `terminal-auth`）→ 按上表拼出两个路径

用户未给出任何可定位信息时，问用户指定哪篇文档，不猜。

### 第 2 步：加载文档（只读三波，读完即止）

1. **story 设计文档**（全读）：功能故事、模块划分、接口清单、关键数据结构、调用关系、AI 编码指南。
2. **develop-task 任务文档**（默认必读）：修改文件清单是编码任务来源，验证方式是验收依据。
   - 文件不存在时：明示"`docs/develop-task/<功能名>-develop-task.md` 不存在"，降级为从 story 文档的模块划分（标注"（规划）"的文件）与接口清单推导修改文件清单，继续编码，并在产出总结开头注明该降级；用户可要求先跑 spec-story-design 补齐后再编码。
3. **外部引用文档**（只读被显式引用的）：
   - story 文档「外部文档引用」章节表格中的链接（关键类 / 接口 / 外部接口 / 基础框架 / 结构文档）
   - develop-task「要用的框架」「要调用的外部接口」章节表格中的链接
   - 标注"无引用"的行跳过；链接失效跳过并在总结中注明
   - **禁止**读取未被引用的文档；文档存在性判定只对推导/引用出的具体文件路径做单次探测，**禁止**列目录浏览找文档

### 第 3 步：定点核实存量代码（最小化读取）

- 修改文件清单中**"修改"类**文件：只读这些文件的改动点上下文（函数级），确认现有签名与实现
- **"新增（规划）"类**文件：文件不存在不读；但读 story / 引用文档中指明的复用样板（如"复用约定见 src/models/db/user.go"）；引用文档已内嵌完整实现样板的，不再重复读取对应代码文件
- 除此以外的代码文件一律不读

### 第 4 步：生成代码

- **任务范围**：develop-task 修改文件清单，逐文件落地；清单外的文件不改
- **业务逻辑依据**：story 文档（时序图各分支、接口清单、关键数据结构、AI 编码指南）
- **写法依据**：被引用 framework-usage 文档的约定 + 第 3 步核实到的存量代码风格
- **冲突裁决**：设计文档与存量代码事实冲突时，以代码为准调整实现，并在总结中列出偏差；story 中标注"需求未明确，待详设确认"的点，编码前一次性列出与用户确认，不脑补

### 第 5 步：验证

- 运行 develop-task「验证方式」章节的命令（构建 / 测试）
- 失败则修复重跑；未跑过验证命令不得宣称完成

### 产出总结（聊天区输出，不生成文件）

生成/修改文件清单 + 降级与失效链接说明 + 冲突偏差 + 验证命令结果。

## 红线（这些想法意味着你正在脱离文档驱动）

| 想法 | 现实 |
|------|------|
| "我先扫一下代码仓结构" | 结构依据在 story 引用的 structure 文档里，不扫仓 |
| "我翻翻 framework-usage 目录还有啥" | 只读被引用的具体文档，不列目录 |
| "这功能可能还涉及别的模块" | 修改范围以修改文件清单为准，不自行扩 |
| "develop-task 不在，跳过不提" | 缺失要明示降级，不是沉默略过的理由 |
| "设计说复用 X，直接写" | 第 3 步定点核实后再写，签名以存量代码为准 |
| "需求未明确的地方我补个合理实现" | 未明确处列出与用户确认，不脑补 |

## 与其它 skill 的关系

- **上游**：spec-story-design——产出本 skill 的两个输入文档（story 设计文档 + develop-task 任务文档）
- **下游（可选串联）**：code-generation-quality-loop——specgo 只负责"按文档把代码写出来并跑通验证命令"；需要 CodeCheck 全量规则扫描、DT/E2E 测试自闭环时，在 specgo 完成后串联它
