# specgo — 规格化全链路编排（主流程）

新功能从需求到交付的唯一编排入口。主代理不亲自分析、设计、编码——只做流程推进、用户确认、子代理派发与验收。

## 分工原则

| 角色 | 职责 |
|---|---|
| 主代理 | 步骤推进与衔接；所有与用户的询问/确认；派发子代理（prompt 含 skill 加载指令+输入+产出+返回要求）；验收子代理产出；每步末组织 ask-human 审视门；汇总报告 |
| 子代理 | 干活：资产分析、建模审核、story 撰写、代码实现与测试、代码检查与修复。每个子代理**第一步必须加载对应 skill 全文**再开工 |

**用户交互中转模式**：子代理执行中遇到需要用户输入的点（断点补齐、疑问澄清、修复决策），不得自行脑补——返回"待确认清单"结束本轮；主代理向用户询问后，把答案回传**同一子代理**（task_id 续会话）继续，不新起子代理重做。

## 固定 ask-human 审视门（最高纪律）

**每个步骤的校验环节结束，固定进入 ask-human 审视门——无一例外：**

1. 主代理列出本步**新生成/修改的全部文档与代码清单**（逐条带路径），附验收结论（mermaid VALID 结果、测试/构建命令结果、待确认项闭环情况），用 AskUserQuestion 询问用户是否审视通过。
2. 用户审视通过 → 才允许进下一步；用户有意见 → 主代理把意见回传对应子代理（task_id 续会话）整改，整改后**重新过同一道门**。
3. 尤其任何**新生成文档**（资产文档、建模 HTML、story/develop-task、刷新后的资产文档、全链路分析报告）必须经人审视后才允许继续执行——子代理自验 VALID/通过不等于门通过，主代理验收通过也不等于门通过。
4. 不默认、不跳过、不替用户回答；用户明确要求"后面都别问了"时，在最终报告中注明被跳过的门。

## 第 1 步：资产检查与录入/刷新

1. 探测四类核心资产目录：`docs/` 下——`biz/interface/`、`tech/usage/`、`tech/comm-guidelines/`、`arch/structure-model/`（README.md 仓级总览 + structure-model-*.md）。
   - 需要全套 16 类资产（含 rules/object-model/data-model/lexicon 等）时，改派 spec-analyze 子代理做一键全量分析，本步后续小步跳过。
   - `docs/business/` 旧体系资产目录（story/key-class/data-structure 等）如存在仅作"外部文档引用"素材，不再探测录入（对应旧分析 skill 已删除）。
2. 分支：
   - **存在** → 询问用户是否需要刷新资产
   - **不存在** → 询问用户是否需要录入资产
   - **选否** → 跳过本步；后续步骤的"外部文档引用"章节按"无引用"处理
3. **选是** → 同一条消息**并行**派发 4 个子代理，每个加载一个分析 skill 全文后执行（可让用户勾选子集，默认全量）：
   - structure → arch-structure-model-analyze
   - interface → biz-interface-analyze
   - comm-guidelines → tech-comm-guidelines-analyze
   - usage → tech-usage-analyze
4. 验收：产出文档落位对应目录；含 mermaid 的文档全部通过 mermaid-validate 验证脚本（VALID）。
5. **审视门**：列出本步新生成/刷新的资产文档清单（带路径）+ VALID 结论，ask-human 审视通过后才进第 2 步。

> 注：交互模型文档（docs/arch/interaction-model/interaction-model-*.md）不属于本步自动检查的资产——它由用户主动指定流程后经 arch-interaction-model-analyze 提取产出，不派全量子代理。

## 第 2 步：需求与功能审核（spec-audit 场景 1）

- 派**审核子代理**：加载 spec-audit 全文，按场景 1（需求/功能设计审核）执行，输入=需求/SR/功能设计文档，完成多彩建模翻译 + 全面扫描（表述质量/逻辑断点/设计要素）+ HTML 初版。
- 子代理返回合并断点清单；**主代理**批量抛出全部问题 ask-human（每问给 2-4 个候选答案+推荐项），用户批量回答后核对——未答/含糊/引入新疑点的继续批量追问，无新问题的答案回传子代理补齐，直至建模闭环、HTML 定稿。
- 审核通过后按 skill 阶段 6 询问用户是否输出规范功能实现设计 md。
- **审视门**：建模闭环后，列出定稿 HTML（及可选的规范功能设计 md）路径，ask-human 审视通过后才进第 3 步。
- 用户明确说"需求已确认、不用审核"时可跳过，并在最终报告中注明。

## 第 3 步：story 设计（spec-story-design）

- 派**设计子代理**：加载 spec-story-design 全文，输入=第 2 步审核通过的 Spec + 第 1 步资产文档（usage 框架指导 + docs/storys 既有 story 为参照）。
- 产出 `docs/storys/{功能名}-story.md`（八类核心要素结构，标注新增/变更/不涉及）+ `docs/develop-task/<功能名>-develop-task.md`。
- 子代理在 develop-task 第 5.2 步返回疑问清单 → 主代理批量向用户澄清 → 回传子代理定稿。
- 主代理验收：story 八类核心要素判定完整（变更条目写清更改对象与内容）、develop-task 修改文件清单到函数级、mermaid 全部 VALID。
- **审视门**：列出 story 与 develop-task 文档路径 + 验收结论，ask-human 审视设计，通过后才进第 4 步。

## 第 4 步：代码实现与测试

**先询问用户**：设计已完成，是否直接开始实现代码？选否 → 停在本步，输出阶段总结。

选是 → 派**实现子代理**，按以下纪律执行：

1. **加载输入文档（只读三波）**：story 设计文档（全读）+ develop-task（修改文件清单=编码唯一任务来源，验证方式=验收依据）+ 两文档**显式引用**的仓内文档；未引用的一律不读，禁止列目录找文档。
2. **定点核实存量代码**：只读"修改"类文件的改动点上下文（函数级）；"新增"类读文档指明的复用样板；其余代码一律不读。
3. **按清单实现**：修改文件清单逐文件落地，清单外不改；设计文档与存量代码冲突时以代码为准并列出偏差；需求未明确处返回待确认清单，不脑补。
4. **单元测试**：覆盖新增/改动逻辑，全部通过。
5. **集成测试**：代码仓存在集成/E2E 测试约定时（仓内测试目录，或 README/AGENTS.md 声明的集成测试方式）**必须主动运行**，不等用户提醒；不存在则跳过并在返回中注明。
6. **验证**：运行 develop-task「验证方式」章节的命令（构建/测试），失败修复重跑；未跑过验证命令不得宣称完成。

返回：生成/修改文件清单 + 冲突偏差 + 验证命令结果 + 集成测试结果 + **实际加载的文档清单**（story/develop-task/显式引用的仓内文档，逐条带路径，供第 6 步报告取证）。

**审视门**：主代理汇总代码变更摘要（git diff 文件清单 + 函数级改动概述）、单测/集成测试与验证命令结果，ask-human 审视代码实现，通过后才进第 5 步；有意见回传实现子代理整改后重新过门。

## 第 5 步：资产刷新（spec-update）

1. 前置：本需求代码变更已就绪。spec-update 以 git 对比为输入——代码已 commit 时基线最清晰；未 commit 也可基于工作区 diff 执行。**是否提交代码由用户决定，不得主动提交**。
2. 派**资产子代理**：加载 spec-update 全文，基于 diff 识别变更映射到各资产要素的受影响情况，产出刷新清单（受影响/不受影响/资产未建三态判定 + 依据）。
3. 子代理返回刷新清单；**主代理交用户审核确认（可勾选子集）后**，子代理按最新要素定义执行增量刷新、定稿落盘。
4. 含 mermaid 的刷新文档必须全部 VALID；资产文档有增删时按 spec-index 口径收口索引。
5. **审视门**：列出本步实际刷新的资产文档清单（带路径）+ VALID 结论，ask-human 审视通过后才进第 6 步。

## 第 6 步：全链路分析报告（收尾必做）

代码生成收口后，产出**需求 → 代码全链路分析报告**，让人一眼看出改了什么、引用的资产靠不靠谱。

1. **取证**（主代理汇总各步骤已返回的事实，禁止凭印象）：
   - 代码修改清单：以 `git diff`（已提交则取本次需求 commit 范围）为唯一事实来源，逐文件核对 develop-task 修改文件清单——清单外改动、清单内未改都要显式暴露；
   - 引用资产清单：story「外部文档引用」章节 + develop-task 框架表 + 第 4 步实现子代理返回的实际加载文档清单，逐条去重合并；
   - 各步骤返回的冲突偏差、待确认事项、验证命令结果（作为资产评估依据，不单独成节）。
2. **派报告子代理**撰写报告（prompt 含上述取证材料 + 模板路径），按 references/specgo-report-template.md 填充，固定两节：
   - **代码修改清单**：文件 / 新增或修改函数 / 变更说明（≤30 字，给人看的一览表，不写代码细节）；清单外改动显式标注；
   - **引用资产质量评估**：每篇引用资产一行——质量是否符合预期（符合/部分符合/不符合）+ 依据与补强建议（指向具体 skill 重跑或文档修订）；生成中靠读代码反推的决策、未闭环要素，必须在此指回具体失实/缺失的资产文档；表后附注未引用但发现失实的资产问题。
3. **落盘**：被分析仓 `docs/specgo-report/{YYYYMMDD}-{功能名}.md`（目录不存在则创建；次抛件带日期，同日同需求重跑同名覆盖）。
4. **审视门**：报告落盘后，ask-human 审视报告全文；有意见回传报告子代理修订后重新过门，审视通过后流程结束。
5. 评估为「部分符合/不符合」的资产，主代理在回复中显式列出并给出下一步建议（如重跑某 analyze skill、补齐某资产后再生成）。

## 子代理派发通用规则

- prompt 四要素：①加载哪个 skill 全文 ②输入文档/数据路径 ③产出路径与格式 ④返回内容（产出文件清单 + 关键结论 + 待确认清单 + 阻塞项）。
- 无依赖的子代理同一条消息并行派发（第 1 步 4 个分析、第 5 步各资产刷新）；步骤间有依赖严格串行。
- 主代理验收不过关就打回子代理整改，不亲自代写。

## 确认门总表

| 节点 | 询问内容 |
|---|---|
| 第 1 步 | 资产存在→是否刷新；不存在→是否录入（可选子集）；**末：新生成/刷新的资产文档 ask-human 审视门** |
| 第 2 步 | 断点批量 ask-human；审核后是否输出规范设计 md；**末：建模 HTML/设计 md ask-human 审视门** |
| 第 3 步末 | **story + develop-task 设计文档 ask-human 审视门** |
| 第 4 步前 | 是否直接开始实现代码 |
| 第 4 步中 | 需求未明确处澄清（子代理返回待确认清单时） |
| 第 4 步末 | **代码变更 + 测试结果 ask-human 审视门** |
| 第 5 步 | 资产刷新清单审核确认（可勾选子集）；代码是否提交由用户决定；**末：刷新后的资产文档 ask-human 审视门** |
| 第 6 步末 | **全链路分析报告 ask-human 审视门**——审视通过后流程结束 |

## 红线

| 想法 | 现实 |
|---|---|
| "步骤简单，我主代理顺手做了" | 分析/设计/编码/检查一律派子代理，主代理只编排与确认 |
| "这个断点/疑问我补个合理答案" | 所有需求疑问走待确认清单→主代理问用户，不脑补 |
| "设计和代码并行跑省时间" | 步骤间严格串行，确认门不过不进下一步 |
| "文档生成了，VALID 也过了，直接进下一步" | 每步校验环节结束固定过 ask-human 审视门——VALID/测试通过只是门的输入，人审视通过才算过门 |
| "代码都测过了，不用再给人看" | 第 4 步末代码变更必须列 diff 摘要 + 测试结果交人审视，通过后才进资产刷新 |
| "报告是收尾交付物，落盘即结束" | 第 6 步报告同样过 ask-human 审视门，审视通过流程才结束 |
| "集成测试等用户提醒再跑" | 仓里有集成/E2E 测试就必须主动运行 |
| "代码写完直接交付" | 第 5 步资产刷新是收口闸门，docs 不同步需求不算完成 |
| "分析报告凭印象总结一下" | 第 6 步报告的修改清单/引用资产评估必须以各步骤返回与 git diff 取证，逐文件逐篇落实，禁止臆造 |
| "commit 一下方便做 diff" | commit 必须用户明确同意 |

## 与其它 skill 的关系

本 skill 是纯编排层，六个步骤分别调用：4 个分析 skill（arch-structure-model-analyze、biz-interface-analyze、tech-comm-guidelines-analyze、tech-usage-analyze，第 1 步；全套 16 类资产录入改用 spec-analyze）、spec-audit 场景 1（第 2 步）、spec-story-design（第 3 步）、spec-update（第 5 步）、全链路分析报告（第 6 步，模板 references/specgo-report-template.md）；mermaid 验证贯穿各步（mermaid-validate）。各 skill 也可脱离本流程单独触发。
