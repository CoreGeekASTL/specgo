# 文档质量审核与评估（spec-audit）

一个 skill 覆盖两类文档质量场景：

| 场景 | 输入 | 干什么 | 产出 |
| --- | --- | --- | --- |
| **场景 1：需求/功能设计审核** | 用户提供的一篇 Spec/需求/功能设计文档（docs/ 资产目录之外） | 多彩建模翻译 + 三类断点扫描 + ask-human 批量澄清，把文档补齐到可供编码 | `docs/audit/{需求名}/` 建模 HTML；可选规范功能设计 md（`docs/storys/`） |
| **场景 2：资产质量评估** | docs/ 已建资产文档（单篇/某类/某域/全仓） | 按《软件设计要素文档质量评估方案》两轨评分定级 | `docs/report/`：`README.MD` 整体评估 + 每篇被评文档一个 `{文档基名}-audit.md` 打分报告（镜像 docs/ 相对路径） |

两场景共享同一套审核机制（多彩建模 + 断点清单 + 澄清循环）；场景 2 的 A 轨直接内嵌场景 1 的阶段 1-3。

**自包含原则**：本 skill 所需模板与方法论文件全部归档在自身 references/ 与 assets/ 目录下，不依赖其它 skill 的文件（mermaid 验证脚本除外，全插件共用）。

## 第 0 步：场景判定

- 用户提供一篇需求/设计文档要求审核/解读/查断点 → 场景 1。
- 用户要求评估 docs/ 资产质量（打分/定级/盘点待改进项）→ 场景 2；评估范围（单篇/某资产类型/某域/全仓）**用户未指定时询问，禁止默认全仓**。
- 同一诉求同时含两者时先场景 1 后场景 2。

## 场景 1：需求/功能设计审核（七阶段，严格按序）

核心思想：把 Spec 文档翻译成多彩建模图（业务事件-角色-实体-描述的因果链路图），逻辑断裂点会在图上自然暴露；同时扫描文档的表述质量问题（成分残缺/弱表述/术语失范/语义多解）；三类问题一次扫描、合并为一份断点清单，统一 ask-human 澄清补齐，最终产出一份可供编码人员审核的 HTML。

### 阶段 1：解读文档，完成多彩建模

1. 通读用户提供的文档全文（Spec/需求/设计文档）。
2. 按 [references/color-modeling.md](references/color-modeling.md) 中的方法论提取四类元素：
   - 粉色「时刻/事件」：业务动作、状态变更、流程节点
   - 黄色「角色」：参与者（人、系统、外部服务）
   - 绿色「实体」：业务对象（人/地/物）
   - 蓝色「描述」：规则、约束、分类、属性说明
3. 按时序/因果箭头连接元素，形成完整建模链路。建模时不臆造文档中不存在的业务规则——不确定的内容标记为「待确认」，留到后续阶段检出澄清。

### 阶段 2：全面扫描，生成初版 HTML

对原文做三类检出，全部结果汇总为断点清单，并生成初版 HTML：

1. **表述质量扫描（必做）**：对照 [references/requirement-quality-checklist.md](references/requirement-quality-checklist.md) 逐条语句扫描 5 大类别——句子成分残缺（缺主语/宾语/触发条件）、弱表述·不可测（弱词黑名单 + 不可测形容词）、术语失范（未定义术语/一词多义）、语义多解·关系不清、带病放行。弱词黑名单用内置默认词表；若被审仓 `docs/audit/weak-words.txt` 存在则追加仓内自定义词，取并集。
2. **逻辑断裂点扫描（必做）**：对照 [references/gap-checklist.md](references/gap-checklist.md) 断点 1-9 逐项检查建模链路的逻辑断裂与逻辑不全。
3. **设计要素校验（功能设计文档必做，纯需求文档跳过）**：若被审文档含实现设计章节，对照 gap-checklist.md 断点 10/11/12 逐项核对——时序图呈现（含分支与异常）、功能验收用例（编号/前置条件/步骤/预期结果）、外部接口与跨服务调用接口信息（接口名/路径/输入输出）。
4. 术语失范与断点 9（术语歧义）重叠的命中**合并为一个断点**，不重复检出。
5. 复制 [assets/model-template.html](assets/model-template.html) 为初版 HTML，将建模结果与全部断点卡片（红色虚线高亮，标注问题类别）填入；保存到 `docs/audit/{需求或功能名}/` 目录（若不存在则创建），文件名 `{需求或功能名}-建模结果.html`。

本阶段只检出、不提问；所有断点进入阶段 3 统一澄清。

### 阶段 3：统一 ask-human 澄清（批量提问循环 + 质量门禁）

1. 将阶段 2 的三类断点合并为一份清单，按严重程度排序编号（阻塞级 🔴 → 风险级 🟠 → 提示级 🟡，分级规则见 gap-checklist.md）。
2. **批量提问**：一次将全部问题抛给用户，不打断多次。每问包含：编号、原文引用（章节/段落）、问题类别、2-4 个具体可执行的候选答案选项（按可能性排序、推荐项标注，不允许"其他"类兜底选项由自己提供）；语义多解类把每条的 N 种理解全部列成候选选项，让人只做选择题。
3. **核对回答，循环追问**：收到用户批量回答后逐问核对——
   - 已明确裁定的：记录为「人工裁定」，标注来源与答复时间；
   - 未回答或回答含糊的：保留进下一轮问题清单；
   - 裁定本身引入新疑点的（答案中出现新的未定义术语、新业务分支、新边界条件）：重新扫描受影响内容，生成新断点并入下一轮清单；
   - 有新问题的再次批量抛出，循环直至无新问题。
4. **质量门禁**：全部断点有人工裁定（已补齐/用户确认接受）后才进入阶段 4。用户选择跳过或明确要求带病继续的，记为「仍存疑」，保留红色标记——表述质量类仍存疑项须在阶段 5 审核提醒中单独列出"表述问题未清零，不建议进入编码"，报告留档归因。

### 阶段 4：完善 HTML，清晰呈现建模结果

1. 把人工裁定回填到模型中，断点卡片转为「已补齐」状态（绿色边框 + 裁定内容）。
2. 完善 HTML 的可读性：
   - 四色图例置顶，非技术人员也能看懂
   - 因果链路按主流程→分支/异常流程分层排布
   - 每个元素卡片标注：所属颜色类别、原文出处（章节/段落）、确认状态（原文明确/人工补齐/仍存疑）
3. 仍存疑的项保留醒目标记，不得悄悄删除。

### 阶段 5：提醒编码人员审核

在最终回复中明确输出「编码人员审核提醒」，包含：

- HTML 文件位置与查看方式
- 审核要点清单：已补齐的断点裁定是否符合真实业务、仍存疑项（表述质量类单独列出）、建模中缺失但编码时必须的细节（异常处理、并发、边界值）
- 明确提示：**HTML 未经编码人员确认前，不得进入编码阶段**

### 阶段 6：按模板输出规范功能设计 md（必须先询问用户确认）

审核完成后，**必须询问用户**是否按 [references/functional-design-template.md](references/functional-design-template.md) 输出一篇规范的功能设计 md——不得跳过询问、不得自行决定输出。用户明确确认后：

1. 按模板章节结构生成：功能概述 / SR 设计 / 实现思路 / 实现设计（含用例时序图）/ 用户接口设计 / 实现接口设计 / 安全配置设计 / 功能规格 / DFX 分析 / 分配需求。
2. 内容来源=原文档已有内容 + 本次审核的人工裁定；实现设计章节的用例必须含时序图（mermaid sequenceDiagram），把补齐后的分支/异常流程画全。
3. 模板中的可选章节无对应内容时标注"不涉及"并裁剪；原文档与裁定都未覆盖的内容标"待确认"，**禁止脑补**。
4. 输出到 `docs/storys/` 目录（功能设计属 story 类资产），文件名 `<功能名>-功能设计.md`；目录不存在则创建。

### 阶段 7：验证产出物中的 mermaid 图（收尾必做）

若产出的规范版 md（或 HTML 内嵌）中含 ```mermaid 代码块（用例时序图等），交付前必须运行 spec-mermaid-diagram skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 spec-mermaid-diagram skill 的「语法红线」。

## 场景 2：docs/ 资产质量评估（六步，严格按序）

### 第 1 步：确定评估范围与分轨

- 评估范围两种模式：
  - **单篇评估**：用户指定一篇文档——只评该篇，第 6 步走「更新模式」（不重评其他文档）。
  - **通篇评估**：某资产类型 / 某域 / 全仓资产——逐篇评估，第 6 步走「全量模式」。
  用户未指定时询问，禁止默认全仓。
- 逐文档分轨：`docs/storys/` 下功能设计 md、`{功能名}-story.md`、`develop-task` → **A 轨**；arch/biz/tech/qual 资产文档与索引 README → **B 轨**。批量评估时按轨分组执行。
- 读取评估基准：B 轨词典类评估须先读 `docs/biz/lexicon/`（术语命中基准）；A 轨 story 评估须先读对应需求文档（变更可追溯的对照源）。

### 第 2 步：Linter 阶段（两轨共跑，规则按适用轨取用）

逐条执行通用层规则检查，输出 **Linter 结果表**（规则 | 命中数 | 位置清单）：

| # | 规则 | 检查规程 | 适用轨 |
| --- | --- | --- | --- |
| 1 | mermaid 渲染校验 | `node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <文档>`，全部 VALID 才算过 | A+B |
| 2 | 代码锚点有效率 | 提取文档引用的代码标识符+文件路径，逐条 grep 核实真实存在；带行号的证据记命中 | B |
| 3 | 链接与导航闭环 | 主文档导航表条目 ↔ 目录实际文件双向比对（多出=游离、缺失=断链）；markdown 相对链接目标存在性检查 | B（A 轨 story 索引同查） |
| 4 | 术语引用校验 | 文档业务术语抽样比对 `docs/biz/lexicon/` 词条，未命中记疑似的未登记术语 | A+B |
| 5 | 术语唯一性 | 同一概念多叫法 / 同一名字多含义（对照词典语境边界列） | A+B |
| 6 | 覆盖自检留痕 | 检查元信息/说明节含扫描数、收录数、差集说明或采样口径 | B |
| 7 | 主语/宾语完整性 | 逐句扫描验收/规则语句缺行为主体或作用对象（判定口径见 [references/requirement-quality-checklist.md](references/requirement-quality-checklist.md)） | A |
| 8 | EARS 句式 | 规则/验收语句触发条件必填；表格化章节以「条件/动作/依据」列结构等价判定 | A |
| 9 | 弱词黑名单 | 内置词表 + `docs/audit/weak-words.txt` 仓内词表取并集（同场景 1 阶段 2 口径） | A |
| 10 | 可测性 | 形容词/副词未量化（"快速""大量""合理"等无指标支撑） | A |
| 11 | 待确认集中登记 | 「代码未体现，待确认」「需求未明确」标注散落在正文但未汇总进清单节 | A+B |

- **零容忍项**（#1-5）任一命中 → 该文档通用层直接判"不通过"，不进计分，报告标注命中清单。
- 扣分项按每处 −1（覆盖留痕缺失 −2）计通用分。

### 第 3 步：反诘 + 映射阶段（A 轨必做，B 轨跳过）

A 轨逐文档执行：

1. **按场景 1 的阶段 1-3 执行**（本 skill 内嵌机制）：多彩建模翻译 → 三类断点扫描 → 断点分级清单 → ask-human 批量澄清循环。
2. **story 文档加查**（场景 2 自有口径，在断点清单中追加）：
   - 八要素三态判定完整性——总览表八行齐全，无遗漏判定；
   - 变更条目可追溯——每个「变更」条目写清变更对象（既有要素+文件）与更改内容（变更前 → 变更后），变更前状态有资产文档或存量代码事实依据；
   - 规划标注合规——规划文件标"（规划）"，复用/变更点指向真实存量文件。
3. **澄清门禁**：全部断点有人工裁定才进第 4 步；用户明确带病继续的，记「仍存疑」——**A 轨澄清未清零不出分**，报告直接判"打回"，残留问题清单入报告。

B 轨跳过本步：资产文档以代码事实为最终依据，歧义消解靠锚点反查与抽样走查，不走反诘。

### 第 4 步：专项维度评分

- 按评估方案专项层找到被评文档所属类型的维度表，**逐维度 0-5 打分**，每维度必须给判据证据（抽样结论、反查命中数、覆盖数字），禁止凭印象给分。
- **抽样走查**：链路/锚点/映射类维度每类抽 1-2 个样本深查（如交互模型抽 1 条时序链路对照代码走查；词典抽 5 个词条 grep 反查）。
- A 级文档清单（功能设计/Story 设计、业务规则、对象模型、领域词典、数据模型、接口）：评分后标注"**需人审专项维度签字**"，报告单列待签清单。

### 第 5 步：计分与分级

- **总分 = 通用分 × 40% + 专项分 × 60%**（专项分 = 各维度均值 / 5 × 100；A 轨通用分取 A 轨适用规则）。
- 分级：**≥90 已基线** / **75-89 待修订** / **<75 重写**；零容忍命中或 A 轨澄清未清零 → 直接"打回"，不进分级。
- 每篇文档给出低分维度（<3 分）的改进建议，建议须落到具体章节/条目。

### 第 6 步：产出评估报告并归档 docs/report/

**每篇被评文档生成一个对应的打分报告 MD**（活文档，同名覆盖更新，不留历史副本、不加日期后缀）：

- 落盘路径：`docs/report/{文档相对 docs/ 的路径}/{文档基名}-audit.md`——镜像 docs/ 目录结构，如 `docs/biz/lexicon/lexicon-login.md` 的报告落 `docs/report/biz/lexicon/lexicon-login-audit.md`；目录不存在则创建。
- 报告结构固定五节：

```
# {文档名} 质量评估报告
| 元信息 | 值 |   # 被评文档路径 / 轨道(A/B) / 评估日期 / Skill: spec-audit
## 1. 评分总览              # 通用分 / 专项分 / 总分 / 分级（或"打回"及原因）
## 2. Linter 结果           # 规则 × 命中数 × 位置；零容忍命中单列
## 3. 反诘澄清结果（A 轨）   # 断点数/裁定数/仍存疑清单；B 轨写"跳过"
## 4. 专项维度得分明细       # 维度 | 得分(0-5) | 判据证据
## 5. 低分项与改进建议       # <3 分维度逐项给落到章节/条目的建议
```

**`docs/report/README.MD` 整体评估**（活文档，结构固定两章节）：

```
# docs 资产质量评估总览
```

**两种归档模式**：

## 关键约束

- **基于实证**：所有检出与判分以实际读到的文档与代码证据为准；锚点反查、链接闭环必须真实执行 grep/文件比对，禁止目测通过。
- **澄清门禁不可跳**：断点未裁定（场景 1）/ A 轨澄清未清零（场景 2）不进下一阶段，用户带病继续记「仍存疑」，禁止给分或放行蒙混。
- **不修改被审/被评文档正文**：场景 1 的补齐只落在建模 HTML 与可选功能设计 md；场景 2 的改进建议只落在报告——docs/ 资产正文的刷新归 all-update，重跑归对应 analyze skill。
- **报告活文档更新**：`docs/report/` 下打分报告与 README.MD 同名覆盖更新，不保留历史副本、不加日期后缀；单篇评估只更新该篇对应的报告与 README 行，禁止顺手重评或改写其他文档的评估结果。
- **文档语言**：产出用中文，代码标识符与技术术语保留英文。
