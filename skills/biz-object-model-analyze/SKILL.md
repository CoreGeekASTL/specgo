# 代码仓对象模型分析 Skill（biz-object-model-analyze）

## 目的

从存量代码仓提取**对象模型**资产——回答三个问题：

1. 这个仓的业务对象有哪些——哪些是实体、哪些是值对象？
2. 聚合边界在哪——谁是聚合根、一致性边界内包含哪些对象？
3. 领域服务与领域事件有哪些、对象之间的关联与跨聚合引用方向是怎样的？

产出：UML 类图（mermaid classDiagram）+ 对象说明表 + 补充说明，落盘被分析仓的 `docs/0-biz/object-model/object-model-{aggregate}.md`，**每聚合 1 篇**。

与数据模型（biz-data-model-analyze，`docs/0-biz/data-model/`）的关系：对象模型回答"运行态的业务对象怎么建"（以代码中的结构体/类为准），数据模型回答"持久态的数据怎么存"（表结构、字段关系与数据生命周期）；两者视角不同，**禁止把 DB 表字段机械照抄成类图**。

两种梳理范围：**单聚合模式**（用户点名聚合，只梳理该聚合）与**全量模式**（用户未指明聚合时的默认模式——扫描模型层与核心 service，按聚合根归集后逐聚合产出，不再询问"梳理哪个"）。

**自包含原则**：本 skill 所需模板归档在自身 references/ 目录下，不依赖其它 skill 的文件。

## 何时触发

- 用户指定某个聚合/领域对象，要求"梳理对象模型"、"画类图"、"整理领域模型文档"、"XX 聚合里有哪些对象"——单聚合模式。
- 用户未指明聚合、或要求"梳理全部聚合"、"把领域对象落成文档"、"做一下 DDD 摸底"——全量模式（默认梳理全部聚合，见第 1 步），**不得阻塞式询问**。
- 用户要求补充某个业务域的对象模型资产（重构前对象盘点、新人上手领域层、AI 编码沉淀对象知识）。

## 工作流程

按下述步骤顺序执行。分析基于**实际读到的代码**，不得臆测；读不到就明确标注"未识别（原因：xxx）"。

### 第 1 步：确定梳理范围，定位模型层

1. **用户指明聚合 → 单聚合模式**：只梳理该聚合。聚合名含糊时（如"订单"但仓内有订单与订单快照两组对象），列出候选让用户选择。
2. **用户未指明聚合 → 全量模式（默认）**：扫描模型层与核心 service，按聚合根归集仓内全部聚合，逐聚合执行第 2~6 步，**不得询问"要梳理哪个聚合"**。
3. **定位模型层**（通用启发式，跨语言适用）：
   - 读构建/包管理文件（`go.mod` / `package.json` / `pom.xml` / `build.gradle` / `Cargo.toml` / `pyproject.toml` 等）确定语言与源码根；
   - 按目录命名约定找模型层（`model` / `models` / `domain` / `entity` / `entities` / `po` / `bean` 等），抽样确认其中是业务数据结构体/类而非纯配置/工具代码；
   - 找核心 service 层（`service` / `services` / `domain/service` 等），确认其实际操作的主要对象；
   - 无独立模型层目录时（对象散落在各模块内），以核心 service 实际读写、且被 dao/repository 层持久化的结构体/类为模型对象候选，识别依据写入文档概述。
4. 全量模式的归集只在模型层与核心 service 范围内进行，**不做全仓通读**；每个聚合的证据来源仍是该聚合实际涉及的代码文件。

### 第 2 步：识别五类对象，划定聚合边界

按下表标准逐个判定模型层中的结构体/类，并记录证据（文件路径）：

| 对象类型 | 识别标准（代码实证） |
| --- | --- |
| 实体（Entity） | 有唯一标识字段（ID/主键映射），有生命周期（状态随业务流程变化），通常被 dao/repository 层读写落库 |
| 值对象（Value Object） | 无标识，按值判等，不可变（构造函数一次成型、无 setter、语言支持时有值语义），可跨聚合共享 |
| 聚合根（Aggregate Root） | 聚合内唯一可被外部直接引用的实体；dao/repository 以其为读写单位（按聚合根标识整体存取）；聚合内其它对象只能经它到达 |
| 领域服务（Domain Service） | 无状态（无承载业务状态的实例字段，字段仅为依赖注入的协作方），编排多个实体/聚合的业务逻辑；与入口 handler/应用服务（接请求 DTO、管事务边界）区分——拿不准时以实读代码为准，并在补充说明注明判定理由 |
| 领域事件（Domain Event） | 表示"业务上已发生的事实"的对象，命名常为 `xxxEvent`，经事件总线/dispatcher/MQ 发布订阅，常见于 events 目录或消息模型 |

归集规则：

- 以聚合根为单位归集，**每个聚合根一篇文档**；聚合根下辖的实体/值对象随根入篇。
- 领域服务归其主要操作的聚合一篇说明；操作多个聚合时归编排重心所在聚合，并在补充说明点明涉及的其它聚合。
- 领域事件归其产生方所在聚合。
- 跨聚合共享的值对象在首次（按聚合根 slug 字典序）出现的聚合文档中展开，其余聚合文档的对象说明表引用该文档链接，不重复展开。
- 判定存疑的对象，类型列写最接近的类型并在职责列注明"待确认"，禁止硬猜。

### 第 3 步：画聚合类图（mermaid classDiagram）

每聚合一张类图，规则：

- **只画聚合内结构 + 聚合间引用方向**：本聚合的五类对象画全；被本聚合引用的外部聚合根只画一个标注 `<<外部聚合>>` 的空壳节点，用箭头表达引用方向，**不展开对方内部结构**。
- **只保留关键属性与关联**：属性列业务关键字段（标识、对外部聚合的引用、业务状态、金额/时间等业务语义字段）；序列化辅助字段、getter/setter、ORM 标签不进图；**方法一律省略**。
- **以代码中的结构体/类为准**：类名、属性名取代码标识符原文；DB 表里有而代码对象里没有的字段不画，代码对象里有而表里没有的计算字段照画——表结构归数据模型资产（`docs/0-biz/data-model/`）。
- **关系符号**：聚合根与内部实体/值对象用组合 `*--`；跨聚合引用用 `-->`（持对象引用）或 `..>`（仅持标识/经 service 间接访问），方向从引用方指向被引用方；领域事件与发布方的关系用 `..>` 并标注"发布"。
- **stereotype 标注类型**：`<<aggregate root>>` / `<<entity>>` / `<<value object>>` / `<<domain service>>` / `<<domain event>>` / `<<外部聚合>>`。
- **语法要点**：泛型集合写作 `List~OrderItem~`（尖括号在部分渲染器解析失败）；关系基数加引号（`"1"` / `"many"`）；关系标签（中文）放冒号后；其余红线（裸 `end` 禁用、关键字不做裸 label 等）见 mermaid-validate skill 的「语法红线」。

### 第 4 步：按模板产出对象模型文档

按 references/object-model-template.md 的骨架产出（概述 + 类图 + 对象说明 + 补充说明）：

1. **概述**：聚合的业务职责、一致性边界（哪些对象必须随聚合根一起保证一致）、对象构成，1~3 句；模型层定位依据（第 1 步）在此一并交代。
2. **类图**：第 3 步的 mermaid classDiagram。
3. **对象说明表**：对象 / 类型（聚合根/实体/值对象/领域服务/领域事件）/ 代码位置（文件路径，不带行号）/ 职责。
4. **补充说明**：2~4 句——聚合不变量（如"OrderItem 只能随 Order 整体读写"）、跨聚合引用方式（持标识还是持对象）、领域服务的编排范围；末尾一行交代与持久态表结构的对应归数据模型资产（已建则给具体文件链接，未建注明"待补"）。

规则：

- 类图与对象说明表必须与代码实际结构一致，禁止臆造类、属性或关联；每个对象、每条边对应真实存在的代码。
- 代码中读不出来、属于业务规约的内容标注"代码未体现，待确认"，禁止脑补。
- 所有内容必须有代码事实依据，证据形式为文件路径（不带行号）。

### 第 5 步：落盘 docs/0-biz/object-model/

- 输出到**被分析代码仓根目录**的 `docs/0-biz/object-model/object-model-{aggregate}.md`；目录不存在则创建（连同 `docs/` 一起创建）。
- `{aggregate}` 实例 slug **从代码标识符派生**：取聚合根类名/结构体名转 kebab-case，如 `Order` → `order`、`AuthSession` → `auth-session`；禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。聚合的中文名只进文档标题，不进文件名。
- 同名文件已存在**直接覆盖更新**——模型文档是活文档，固定名、覆盖更新，git diff 即演进史。
- **资产主文档 `README.md` 必产出**：同目录落 `README.md`（活文档，同名覆盖），内容仅两项——元信息表（分支/更新日期/Skill）+ 聚合导航表（聚合名 → `object-model-{aggregate}.md` 链接 + 聚合根 + 一句话说明，从各文档首行标题提取）；单聚合模式（用户指定聚合）时同样刷新该 README，只增改对应行。

### 第 6 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块，交付前必须运行 mermaid-validate skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/mermaid-validate/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 全量模式：全部产出文档一次性传入校验；全部 VALID 后在回复中给出汇总——聚合清单（聚合名 → 文档路径）。

## 输出模板

严格按 references/object-model-template.md 骨架填充——只填占位符、表格行、图；写作规则见上文各步骤与「关键约束」。

## 关键约束

- **通用性**：本 skill 不依赖任何特定代码仓的结构与语言。执行时基于实际探测结果走，禁止凭仓库名或已知项目结构臆测。
- **全量模式默认**：用户未指明聚合时默认扫描模型层与核心 service、按聚合根归集逐篇产出，禁止以"先确认范围"、"先问清聚合"为由阻塞。
- **基于实证**：所有对象类型判定、关联与引用方向结论必须有代码支撑，证据形式为 `文件路径`，**不得出现代码行号**，行号会随代码变更失效且无跨工具稳定性。
- **以代码对象为准**：类图以代码中的结构体/类为准，禁止把 DB 表字段机械照抄成类图；持久态表结构归数据模型资产（biz-data-model-analyze）。
- **聚合粒度**：每聚合 1 篇，类图只画聚合内结构与聚合间引用方向；外部聚合不展开内部结构，只画空壳节点与引用箭头。
- **只读不改**：只读、只分析、只产出文档，不改动被分析代码仓的任何文件（新建 `docs/0-biz/object-model/` 目录和文档文件除外）。
- **语言无关**：不预设被分析仓的语言/框架，按第 1 步实际探测结果走。
- **实例 slug 从代码标识符派生**：`{aggregate}` 取聚合根类名/结构体名转 kebab-case，禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。
- **活文档覆盖更新**：`docs/0-biz/object-model/` 下模型文档同名直接覆盖，不保留历史副本、不加日期后缀——差距报告才带日期，模型文档不带。
- **索引分工**：本资产目录的 `README.md`（聚合导航主文档）由本 skill 产出，活文档同名覆盖；域索引 `docs/0-biz/README.md` 与总索引 `docs/README.md` 由 spec-index skill 统一生成，本 skill 不维护。
- **成品纯净**：最终文档只含成品内容（标题、概述、图、表格、补充说明）。模板顶部的元说明、写作指令行、占位符说明均为规则，不复制进成品。第 1~2 步的探测过程（执行的 grep/rg 命令、命中输出摘要）仅供自检，绝不写入最终文档——其结论须以 `文件路径` 证据形式进入相关表格，且**证据不得含代码行号**。
- **文档语言**：输出文档用中文，技术术语（Entity / Value Object / Aggregate Root / Domain Service / Domain Event 等）保留英文。
