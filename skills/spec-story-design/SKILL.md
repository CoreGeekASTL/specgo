# Story 设计：从需求文档到 story 设计文档

接收一篇需求设计文档，结合存量架构资产（framework-usage 框架指导 + story 功能文档），产出一篇**与 docs/story/ 既有功能文档格式与内容一致**的新 story 设计文档。

与存量接口分析类 skill 的本质区别：本 skill 面向**尚未实现的新功能**，证据两源为「需求文档章节」与「存量代码文件（复用点/注入点）」，规划中的文件路径标注"（规划）"；存量分析类 skill 面向存量代码的事实归纳。

**自包含原则**：本 skill 所需模板与方法论文件全部归档在自身 references/ 目录下，不依赖其它 skill 的文件。

## 工作流（顺序不可颠倒）

### 第 1 步：读取需求文档，提取设计输入

从需求设计文档中提取：功能概述与业务价值、外部接口清单（方法/路径/说明）、流程机制（含分支与异常）、数据结构需求、非功能设计（性能/可靠性/安全）、词汇表、Story 划分与依赖、鉴权注入点等对存量链路的修改点。提取时标注需求文档章节号（如"需求 §2.2.3"）。

### 第 2 步：分析存量资产

1. **docs/framework-usage/**：确定新功能应使用哪些基础框架及其约定（路由怎么注册、DAO 怎么继承、缓存怎么写、测试怎么搭），候选框架逐条核对，只保留新功能真实需要的。
2. **docs/story/**：确定新功能与既有功能的关系——复用哪些模块（如统一响应封装、ORM 基座）、在哪些既有链路上注入（如登录/事件上报）、格式基准以哪篇为准。
3. **docs/key-class/（必须）**：确定新功能复用哪些关键类、在哪些关键类上注入行为（如登录链路注入鉴权）——「外部文档引用」章节关键类行的素材来源，仓内无此目录时在回复中提示可先跑 spec-key-class-analyze 补齐。
4. **docs/interface/、docs/external-call/、docs/structure/**：分别确认既有接口注入点、新功能需调用的外部服务契约、新模块的分层归属依据——同为「外部文档引用」章节素材来源。
5. **目标功能文档存在性判定（决定第 6 步是修改还是新增）**：检查 `docs/story/` 下是否已有**同功能域**文档。判定依据按优先级：需求文档所述功能名与既有文档功能名一致 → 业务语义相同（解决同一业务问题）→ 核心模块高度重叠。判定结果二选一：
   - **已有同功能域文档** → 本需求是对该功能的增强/迭代，第 6 步走「修改既有文档」分支
   - **无同功能域文档** → 第 6 步走「新增文档」分支
   - 归属拿不准时：列出判定依据（功能名/语义/模块重叠度）与用户确认，不擅自决定——改错文档比多问一句代价大
6. **存量代码（按需抽查）**：仅核实复用点/注入点的真实文件路径与分层约定（models/dao/service/controllers/routers），禁止全仓阅读。

**存量资产缺失时的降级（任一缺失不阻断流程）：**

- `docs/story/` 不存在或为空：跳过关系分析（无复用/注入对象），格式基准直接采用 references/story-template.md；归档时新建目录并从模板一生成 README.md 索引。
- `docs/framework-usage/` 不存在：跳过框架分析，「外部文档引用」章节基础框架文档类注明"仓内无框架使用文档"，并在 README 索引注明。
- `docs/key-class/` 不存在：「外部文档引用」章节关键类行注明"仓内无关键类文档"，并在回复中提示可先跑 spec-key-class-analyze 补齐。
- `docs/interface/`、`docs/external-call/`、`docs/structure/` 不存在：「外部文档引用」章节对应行注明"仓内无该类文档"。
- 两者均不存在（全新仓首篇 story 设计）：格式基准与多彩建模方法论仍以本目录两个参考文件为准（story-template.md、color-modeling.md），产出物形态不变。

### 第 3 步：先完成多彩建模（L1 功能故事）

**必须先完成本节，再进入第 4 步。**按 references/color-modeling.md 方法论：

1. **实现逻辑速览**：1~3 句，每句 ≤30 字，概括设计后的实现逻辑（业务语言，禁文件名/函数名）。
2. **四色建模图**（mermaid flowchart + classDef 固定配色：粉 #ffd1dc / 黄 #fff3b0 / 绿 #c8e6c9 / 蓝 #bbdefb）：粉色事件链来自需求文档的流程机制（主干时序+分支），黄色角色含内外部系统边界，绿色实体标注状态变更（含缓存等内存态实体），蓝色规则挂实体（校验规则/规格上限/逃生策略）。每个粉色事件必须具备 触发者/输入/输出/后继 四要素。
3. **术语表**：需求文档词汇表 + 既有 story 文档术语的并集，每条=一句话人话解释+出处（需求章节号或存量文件），禁止只写英文全称。
4. 需求未明确的业务细节标注"需求未明确，待详设确认"，禁止脑补。

### 第 4 步：再完成其它设计（L2/L3）

按 references/story-template.md 的格式（与 docs/story/ 既有文档同构）依次产出：

1. **模块划分**：mermaid 依赖图 + 承载功能表。映射到本仓既有分层（controllers/service/dao/models/routers），新模块标"（规划）"，复用模块标"（复用，<文件>）"，职责边界遵循需求文档的模块职责约束。
2. **接口清单**：只列对外接口（含新增接口与既有链路的注入点，注入点单独标注"注入"），五列表格：接口 | 路径/入口 | 请求结构 | 响应结构 | 状态（新功能接口状态取"设计中"）。
3. **关键数据结构**：表格，含表结构需求（字段/约束/索引）、内存结构（缓存项）、文件格式（如 CSV 列定义），定义位置标"（规划，<文件>）"。
4. **调用关系**：每条主链路一张 mermaid 时序图（如管理链路、业务链路分开画），需求中的分支（逃生态、缓存命中/未命中、校验失败整批拒绝）用 alt/opt 表达。**每条调用链补充实现说明**：时序图下方用多句话逐步说明该链路的实现逻辑，每句话 ≤30 字、表达一个完整实现点，业务语言、可落到编码。
5. **AI 编码指南**：1-5 条，每条 ≤30 字，面向"按本设计编码时"的落地规则（分层归属、复用约束、双 DDL、测试方式），附依据（需求章节号或存量文件）。
6. **外部文档引用**：三列表（文档类型 | 引用文档 | 引用点），五类逐行列出本设计参考的仓内规格化资产——**关键类（必须引用）**：列出本设计复用/注入的具体关键类名并链接 docs/key-class/README.md；**接口文档**：链接 docs/interface/ 相关子文档（既有链路注入点依据）；**外部接口文档**：链接 docs/external-call/ 相关子文档（外部服务调用契约）；**基础框架文档**：逐个框架一行，链接到 docs/framework-usage/ 真实存在的文档，用途注明"按该文档 <某约定> 执行"，只列新功能真实需要的框架，禁止按目录全量罗列；**struct 结构文档**：链接 docs/structure/ 文档（分层归属依据）。链接必须指向仓内真实存在的文件，无死链；某类确无引用须注明"无引用"及原因（仓内无对应目录时按第 2 步降级规则注明），禁止整节省略。

### 第 5 步：生成 develop-task 文档（读源码 → 疑问澄清 → 定稿）

本步独立于 story 设计文档，产出辅助出代码的抛弃式文档 `docs/develop-task/<功能名>-develop-task.md`。与第 4 步的设计论证不同——本步只回答"代码怎么改"，依据是**实读源码**而非设计推断。**子步骤顺序不可颠倒，5.2 未完成不得进入 5.3。**

#### 5.1 阅读源码，定位修改点

基于第 4 步产出的模块划分、接口清单、关键数据结构、调用关系，定位存量代码中的复用点 / 注入点 / 新增点，逐一打开相关源码文件阅读：

- 按分层逐一核实：`controllers/`（路由注册方式、Controller 方法签名）、`service/`（接口+实现类+sync.Once 单例）、`dao/`（BaseInterface 继承、EntityType）、`models/`（orm 标签、TableName、init 注册）、`routers/`（路由注册函数）。
- 复用点：确认待复用的函数 / 结构体 / 工具方法的真实签名与调用方式。
- 注入点：确认被注入链路的既有代码结构（如登录 Controller 的鉴权调用位置）。
- 新增点：确认新文件应放置的目录与命名约定（对照存量同类文件）。

禁止全仓通读；只读与修改点直接相关的文件。

#### 5.2 根据需求与源码列出疑问点，提交用户澄清

基于 5.1 源码阅读，对照需求文档，找出歧义 / 多种实现选择 / 需求未覆盖的边界，逐条列出疑问点，**暂停并提交用户，等待澄清后继续**。每条疑问点包含：

- **疑问描述**：一句话说清问题
- **涉及源码位置**：文件路径 + 函数名 / 行号
- **可选方案**：列出 2~3 个候选实现路径及其取舍
- **需要用户决策的问题**：一句话提问

示例：

> **Q1**：`service/auth_service.go` 的 `CheckAuth` 当前无缓存参数，注入缓存有两种方案——(a) 改函数签名加 cache 参数（影响所有调用方）；(b) 在函数内部直接持有 cache 实例（侵入小但耦合）。需求 §3.2 未明确缓存生命周期归属。倾向 (b)，请确认。

无疑问点时也要明确回复"无疑问点，直接定稿"，不得跳过本子步骤。

#### 5.3 用户澄清后，输出完整 develop-task 文档

收到用户澄清回复后，按 references/develop-task-template.md 模板输出完整文档到 `docs/develop-task/<功能名>-develop-task.md`。文档两部分核心内容须基于 5.1 源码阅读 + 5.2 用户澄清填写，输出格式见模板：

- **修改文件清单（模板第 2 节）**：逐文件逐函数列出修改点（图表呈现，格式与要求见模板）
- **澄清问题列表（模板第 7 节）**：5.2 疑问点与用户澄清结论逐条记录（格式见模板）

同名文件已存在时直接覆盖（抛弃式，不维护历史），不进 README 索引。框架与外部接口必须链接仓内真实存在的文档；无对应目录时按需求列出并注明"待核实"，禁止臆造链接。

### 第 6 步：归档与索引

按第 2 步的存在性判定结果二选一：

**分支 A：新增文档**（无同功能域文档）

- 输出到 `docs/story/feature-<功能名>.md`（英文短名 kebab-case）；目录不存在时新建。
- 更新 `docs/story/README.md`：功能全景表新增一行（接口数注明"设计中"），接口统计同步累加；README 不存在时按模板一从头生成。

**分支 B：修改既有文档**（已有同功能域文档）

- 在既有 `feature-<功能名>.md` 上**按节更新**，禁止整篇重写覆盖：
  - L1 功能故事：新事件链并入既有建模图（新增事件/角色/实体/规则直接补入），实现逻辑速览按需改写，术语表取并集
  - 接口清单：新增接口补行、状态标"设计中"；注入点在既有链路接口上补注
  - 调用关系：新增链路补画时序图，既有链路被改动的在对应时序图上体现
  - 关键数据结构 / AI 编码指南 / 外部文档引用：增量补充，与既有内容去重
  - 既有文档含旧版「框架引用」节时：其内容并入「外部文档引用」的基础框架文档行类，并删除原「框架引用」节
- 文档头元信息行注明最近更新来源（如"最近更新：<需求文档名>，YYYY-MM-DD"）。
- 更新 `docs/story/README.md`：该功能行接口数累加（注明"N 新增（设计中）"），不新增行。

**两个分支都要做的：**

- 与既有功能存在注入关系的，在被注入功能文档的接口清单中将对应接口状态补充标注（如"27.0 起注入终端鉴权"）；无既有文档时跳过本项。

### 第 7 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块（L1 四色建模图、调用关系时序图等），交付前必须运行 spec-mermaid-diagram skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 spec-mermaid-diagram skill 的「语法红线」。

## 质量检查清单

- [ ] 第 3 步多彩建模先于 L2/L3 完成，图中每个粉色事件四要素齐全、无文件名/函数名/行号
- [ ] 实现逻辑速览 1~3 句、每句 ≤30 字
- [ ] 产出文档为七节结构（功能故事/模块划分/接口清单/关键数据结构/调用关系/AI 编码指南/外部文档引用），前六节与 docs/story/ 既有文档同构
- [ ] 「外部文档引用」章节五类齐全：关键类已必须引用且列出具体类名；基础框架文档逐个框架一行、链接到存在的 framework-usage 文档、未全量罗列；其余类无引用时已注明"无引用"及原因（仓内无对应目录时已按降级规则注明）；引用链接均指向仓内真实文件，无死链
- [ ] 规划文件均标注"（规划）"，复用/注入点均指向真实存量文件，无臆造路径
- [ ] 接口清单只含对外接口；注入点在表格中单独标注
- [ ] 术语表覆盖需求词汇表与全文黑话；需求未明确处标注"需求未明确"而非脑补
- [ ] AI 编码指南每条 ≤30 字、有依据
- [ ] 已按存量文档存在性判定选择「修改既有文档」或「新增文档」，归属拿不准时已与用户确认
- [ ] 修改场景：既有文档按节增量更新、未整篇覆盖，文档头已注明最近更新来源
- [ ] 每条调用链时序图下方已补实现说明，多句话逐步说明，每句 ≤30 字
- [ ] develop-task 文档已在第 5 步独立产出：5.1 已实读源码定位修改点；5.2 已根据需求与源码逐条列出疑问点提交用户澄清（无疑问时已明确回复"无疑问"）；5.3 按用户澄清定稿七节齐全（修改文件清单图表写到函数级 + 澄清问题列表逐条记录），框架/外部接口链接仓内真实文档
- [ ] README.md 索引已同步（新增场景加行 / 修改场景更新对应行；不存在时已从头生成），无死链
- [ ] 产出文档中的 mermaid 图已全部通过本地渲染验证（spec-mermaid-diagram 验证脚本全部 VALID）
