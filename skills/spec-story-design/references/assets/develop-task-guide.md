# develop-task 编写执行指令

> 本文件由 spec-story-design SKILL 第 7 步读取执行。**输入前提**：story 设计文档已定稿归档（要素变更总览与实现方案是本指令的设计输入）。**产出**：抛弃式施工单 `docs/1-storys/{功能名}/{功能名}-develop-task.md`（同名覆盖、不进 README 索引）。本文档只回答"代码怎么改"，依据是**实读源码**而非设计推断。

## 方案选型铁律（不可协商）

- **业务逻辑正确性第一**：实现方案必须立足第 1 步实读到的存量代码现状（既有分层、既有模式、既有校验与事务边界、并发与边界条件）论证，禁止脱离代码凭空设计；**禁止默认选改动最小、侵入最小的"最简单方案"**——改签名、改调用方、新增中间层等成本较高的方案，只要业务逻辑正确性更优就必须作为候选提交用户拍板；禁止引入逻辑缺口（绕过既有校验/状态机、破坏事务一致性、忽略并发竞争、吞掉异常分支、为少改文件而错位分层）。每条修改点须能对应业务正确性依据（需求章节号 + 存量代码事实），而非仅"改动小/侵入低"。
- **正交四原则**（orthogonality-principles.md）：定位修改点时核对目标分层归属符合 SoC 与稳定依赖方向；每条修改点不得引入重复实现、错位分层、多余依赖、反向/循环依赖。与"业务逻辑正确性第一"冲突时，以业务逻辑正确性为准，并把取舍提交用户确认。

## 第 1 步：实读源码，定位修改点

基于 story 的要素变更总览与实现方案，定位存量代码中的复用点 / 注入点 / 新增点，逐一打开相关源码文件阅读：

- 按分层逐一核实：`controllers/`（路由注册方式、Controller 方法签名）、`service/`（接口+实现类+单例方式）、`dao/`（基类继承、实体注册）、`models/`（orm 标签、TableName、init 注册）、`routers/`（路由注册函数）——按仓内实际分层等价物对照。
- 复用点：确认待复用的函数 / 结构体 / 工具方法的真实签名与调用方式。
- 注入点：确认被注入链路的既有代码结构（如登录 Controller 的鉴权调用位置）。
- 新增点：确认新文件应放置的目录与命名约定（对照存量同类文件）。

禁止全仓通读；只读与修改点直接相关的文件。源码位置一律写文件路径 + 函数名，**禁止行号**（行号随代码变更失效）。

## 第 2 步：task 拆分

把修改点编组为若干个 Task：

- **口径**：按相对独立的功能块 / 业务链路编组——一个 Task = 一块可独立实现、独立验证的功能。
- **文件归属唯一**：同一文件只允许出现在一个 Task 内；跨 Task 的公共改动（新增枚举 / 基础 struct / 公共常量等）归入序号最小的基础 Task，其它 Task 以「前置 Task」依赖之。
- **依赖标注**：Task 间依赖用「前置 Task」显式标注；无前置的 Task 可并行实施。
- **不强拆**：改动单一或量少时一个 Task 即可。
- 拆分结果**不单独打断用户**，随 SKILL 第 8 步设计报告一并交用户审视。

## 第 3 步：条件触发澄清（非必经）

需求语义澄清已在 spec-requirement-audit 闭环，本步**不重复澄清需求**——仅当第 1 步实读源码后发现以下情形才提问：

- 设计假设与代码事实冲突（如 story 假定的既有行为与代码不符）；
- 多种实现方案并存且影响业务正确性，无法自行拍板（如改函数签名影响全部调用方 vs 函数内部持有依赖）。

提问走**文件先行**口径：

1. 先把全部疑问点落盘 `{功能名}-待澄清清单.md`（story 同目录，逐轮同名覆盖）——每问含：编号 / 疑问描述（一句话说清不确定点）/ 涉及源码位置（文件路径 + 函数名，禁行号）/ 候选选项 2-4 个（推荐项标注并附代码依据，不提供"其他"兜底）/ 用户裁定填写位。
2. 再按交互双模式交互：**默认**落盘后用 ask-human 批量提问（用户也可直接在文件里作答，以文件内容为准）；**报告模式**落盘后不再询问，等用户裁定文档内容、发新消息作答。
3. 用户批量答复后逐问核对：未答 / 含糊 / 答案引入新疑问的，再批量追问一轮（文件轮次+1），直至全部问清；闭环后文件保留作裁定留痕。

未触发上述情形时直接进第 4 步定稿，决策记录节写"无"。

## 第 4 步：按 task-template.md 定稿

按 task-template.md 产出单文档多 Task 结构：任务概述 → 任务拆分总览 → 逐 Task 四小节（修改文件清单 / 逐文件改动详情 / 测试清单 / 验证方式）→ 决策记录。写作要点：

- **新增类改动必须给出完整契约**：新文件落位与命名依据、函数/接口签名、字段列表、错误码/枚举取值——直给，开发者无需回 story 反查。
- **修改类改动**：函数级改动点（文件 + 函数名，无行号）+ 行为对照表（场景 | 变更前 | 变更后，穷举所有受影响分支，不变标"不变"）+ 具体改法（代码级，允许代码符号）。
- 参考的仓内文档链接必须指向真实存在的文件，无死链；无对应资产时注明"待核实"，禁止臆造链接。
- mermaid 不强制；如出现，按 `<specgo插件目录>/skills/spec-analyze/references/mermaid-guide.md` 的「语法红线」逐图自查（本产出非资产文档，不跑验证脚本）。
- 同名文件已存在直接覆盖（抛弃式，不维护历史）。

## 自检清单（定稿后逐项过）

- [ ] 已实读源码定位全部修改点，无凭设计推断落笔的改动
- [ ] task 拆分合规：同一文件只归属一个 Task；公共改动归入基础 Task；前置依赖标注完整；改动单一时未强拆
- [ ] 澄清未漏：设计与代码冲突 / 影响业务正确性的多方案已全部问清（或确认无此情形直接定稿）
- [ ] 新增类改动完整契约直给（签名/字段/错误码/枚举），修改类改动行为对照表穷举分支
- [ ] 每条修改点有业务正确性依据（需求章节号 + 存量代码事实），无逻辑缺口，无正交四原则违规（或取舍已经用户确认）
- [ ] 无行号、无 TODO 式占位、链接无死链；mermaid（如有）按红线自查通过
