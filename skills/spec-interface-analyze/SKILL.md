# 代码仓对外接口文档生成

从存量代码仓出发，盘点**本仓对外提供的接口**（服务自己暴露给外部调用的入口），按功能分组产出**一个主文档 + 多个子文档**，归档到 `docs/interface/`。主文档为 `README.md`（目录索引惯例），子文档以 `spec-` 开头。

> 注意：本 skill 的"对外接口"= 本仓作为服务端暴露给外部调用的入口（HTTP 路由 / RPC service / 消息订阅 handler / IDL 契约），**不是**本仓调用别人的接口（那是消费侧）。仓内模块间的语言级 interface 契约不算对外接口，不纳入。

分析遵循四步轻量工作流：

1. 明确范围与排除目录
2. 扫描对外接口注册点（脚本 + 交叉核对）
3. 产出主文档 + 各功能域子文档
4. 输出后自检（防漏文件、防臆造）

## 第 1 步：明确范围与排除目录

- 确认代码仓路径、主要语言、Web 框架（Beego/gin/Spring/FastAPI 等）。
- 确认排除目录（生成代码、第三方 vendor）。默认排除：`vendor/` `node_modules/` `third_party/` `*_gen/` `*.pb.go` 等；测试目录**默认纳入**（测试中的路由/订阅也列出，标注"仅测试使用"）。
- 确认是否包含消息订阅/定时任务入口：默认包含（异步入口也是对外提供的服务能力）。

## 第 2 步：扫描对外接口注册点

两条线并行，再交叉核对：

1. **IDL/契约文件**：查找 `*.proto`、`*.thrift`、`*.graphql`、OpenAPI/Swagger `*.yaml` 等接口契约文件，提取 service/rpc/path 定义。
2. **代码扫描**：运行内置扫描脚本：

```bash
python3 <skill_dir>/scripts/scan_interfaces.py <repo_path> -o scan_result.md
# 可选：--lang go|java|cpp|python 限定语言；--format json 结构化结果
```

脚本扫描三类对外接口注册点：
- **IDL/契约类**：proto service/rpc、thrift service、OpenAPI paths、GraphQL Query/Mutation/Subscription
- **框架路由类**：HTTP/RPC 入口注册点（Beego/gin/echo/chi、grpc Register、net/http HandleFunc、Spring MVC 注解、Dubbo、FastAPI/Flask/Django、C/C++ 注册表、自封装 RouteMapping）
- **消息/事件订阅类**：MQ 消费订阅、事件注册、定时任务入口

3. **交叉核对**：IDL 契约与代码实现交叉核对——有契约无实现=未落地；有实现无契约=自研隐式接口。注意"易遗漏项"（IDL 生成代码虚增、同接口多实现、消息/事件订阅未走显式定义、宏/表驱动注册、网关透传、Beego 注解路由、自封装路由表、已下线接口）。详见 references/interface-catalog.md。
4. **按功能分组**：将扫描到的接口按业务功能聚类（如"用户认证""白名单管理""配置同步"），**禁止按技术层命名**（如"controller 层"）。聚类依据按优先级：路由路径前缀 → controller/service 归属 → IDL service 分组 → 业务语义相近。每功能一般 2~10 个接口；超过 10 个考虑拆分；只有 1 个接口且语义独立时允许单独成功能域。

## 第 3 步：产出主文档 + 各功能域子文档

产出结构如下，归档到 `docs/interface/`：

```
<repo>/docs/interface/
├── README.md                          # 主文档：接口全景 + 功能域索引 + 全局风险
├── spec-interface-<功能名1>.md        # 子文档：该功能域的定位 + 接口表 + 表下数据结构 + 风险
├── spec-interface-<功能名2>.md
└── ...
```

**命名规则**：
- 主文档：`README.md`（目录索引惯例，不以 `spec-` 开头）
- 子文档：`spec-interface-<功能名>.md`，功能名用英文短名 kebab-case（如 `spec-interface-login.md`、`spec-interface-file-mgmt.md`）
- 子文档必须 `spec-` 开头，统一放 `docs/interface/`

**主文档 `README.md`** 结构：
1. **固定元信息表**（表格形式，行结构固定，放文档开头）：

   | 元信息 | 值 |
   |--------|-----|
   | 代码仓 | <仓库名> |
   | 分析基准 | <分支名> 分支 (<YYYY-MM-DD>) |
   | 更新时间 | <YYYY-MM-DD> |
   | Skill | spec-interface-analyze |
   | 主要语言 | <语言> |
   | Web 框架 | <框架及版本，未识别写"未识别"> |
   | API 契约 | <契约文件类型与数量，无则写"无"> |

2. **接口全景**：一张 mermaid 图（本仓为中心节点 → 各功能域节点，节点按业务功能命名）+ 接口统计（HTTP/RPC/消息订阅 各多少、功能域数、接口总数）
3. **功能域索引表**：功能名 | 接口数 | 核心模块 | 子文档链接（链接到对应子文档，无死链）
4. **全局风险与注意点**：跨功能域的共性风险（如全局中间件、双 server 架构、鉴权策略等），每条带证据

**子文档 `spec-interface-<功能名>.md`** 结构（每个功能域一份）：
1. 元信息（功能名、接口数、所属 server 外部/内部）+ 返回主文档链接
2. **定位**：一句话说明该功能解决什么业务问题
3. **接口表格**：列含 接口名 | 作用 | 所在文件 | 方法/路径（HTTP 填 `POST /api/v1/xxx`，RPC 填 `UserService.GetUser`，消息订阅填 `Consume topic-xxx`，定时任务填 cron 表达式）
4. **表格下方逐个接口的数据结构说明**：针对接口表格里的每个接口，说明其请求与响应数据结构（结构名 + 定义位置 + 关键字段+约束），同功能内多接口共用的结构只在首次出现处详述，后续注明"同上"
5. **该功能风险与注意点**（可选）：该功能域内的风险点，每条带证据

**人类友好硬性要求**：

- 每个功能域一个子文档，**按业务功能命名**，禁止按技术层命名。
- 接口必须用**表格**列出（接口名/作用/所在文件/方法或路径），禁止散文段落描述单个接口。
- **"所在文件"列只填文件路径，不带行号**（如 `controllers/login_controller.go`）；其余需精确定位的证据锚点（如风险点、连接配置）保留 `文件:行号` 格式。
- 每个接口的请求/响应数据结构**写在接口表格下方**，逐个接口说明，不要把所有数据结构堆成一张孤立的大表。
- 数据结构只列关键字段与约束，不整段搬运 struct 定义；超过 8 字段只列关键。
- 主文档功能域索引表每行带子文档链接，可从总览直跳详情；子文档元信息带返回主文档链接。
- 单功能域接口数 > 10 时，列代表性 5~10 处并注明"全量见 xxx"，禁止全量罗列刷屏。

**更新策略**：`docs/interface/` 下文档已存在时按功能域逐篇对比更新（功能已下线则标注"已下线"并保留子文档灰显，或从索引移除并归档），不要整目录覆盖重写；主文档索引随功能增删同步更新。

## 第 4 步：输出后自检（防漏文件、防臆造）

文档产出后、交付前必须执行差集自检。漏文件的根因通常是"扫描到了但归类时丢了"，靠通读复查很难发现，必须用清单比对：

1. **生成全量清单 A**：从第 2 步扫描结果（scan_result）提取全部接口标识（HTTP 填 `方法+路径`，RPC 填 `Service.Method`，消息订阅填 topic，定时任务填 cron）。
2. **生成已记录清单 B**：从已产出的各子文档接口表格 + README"未归类接口"节提取全部接口标识。
3. **差集比对**：
   - **A − B（漏记）**：逐个处理——补入对应功能域子文档，或写入 README"未归类接口"并说明理由。禁止静默丢弃。
   - **B − A（多出）**：逐条核实——是动态注册/宏展开等扫描盲区（保留并注明依据），还是臆造（删除）。
4. **文件维度反查**：列出第 2 步命中过注册点模式的全部源码文件，确认每个文件至少被一个功能域子文档的"所在文件"列引用；未被引用的文件逐个追查——要么有接口漏记，要么在自检结论里写明该文件无对外接口的理由（如纯内部 helper）。
5. **自检结论写入 README**：在功能域索引表后加一行自检结论，格式：`自检：扫描 N 个接口，已记录 N 个，未归类 M 个（见上表），差集已清零（YYYY-MM-DD）`。差集未清零的禁止交付。

## 第 5 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块（接口全景图等），交付前必须运行 spec-mermaid-diagram skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 spec-mermaid-diagram skill 的「语法红线」。

## 质量检查清单

交付前逐项确认：

- [ ] 三类对外接口（IDL 契约/框架路由/消息订阅）全部排查过，未命中类目已确认"确实没有"
- [ ] **已执行第 4 步差集自检：扫描清单与文档清单差集清零，命中注册点的源码文件均被功能域引用**
- [ ] README 开头为固定元信息表（代码仓/分析基准/更新时间/Skill/主要语言/Web 框架/API 契约）
- [ ] README 含自检结论行（扫描数/已记录数/未归类数/差集清零日期）
- [ ] IDL 契约与代码实现已交叉核对，生成代码未虚增接口统计
- [ ] 同接口多实现已全部列出并标注选择机制
- [ ] 产出 1 个主文档 `README.md` + N 个子文档 `spec-interface-<功能名>.md`，归档在 `docs/interface/`
- [ ] 主文档含 mermaid 接口全景图 + 功能域索引表（含子文档链接，无死链）+ 全局风险
- [ ] 每个子文档含：定位 / **接口表格** / **表下逐接口数据结构说明** / 该功能风险（可选）+ 返回主文档链接
- [ ] 接口表格列含 接口名 / 作用 / 所在文件 / 方法或路径，无段落式散文
- [ ] **"所在文件"列只填文件路径，不带行号**；风险点等证据锚点保留 `文件:行号`
- [ ] 每个接口的请求/响应数据结构写在接口表格下方逐个说明，共用结构注明"同上"
- [ ] 数据结构只列关键字段与约束，未整段搬运 struct 定义
- [ ] 功能域按业务功能命名，无"controller 层""service 层"等技术层命名
- [ ] 子文档文件名符合 `spec-interface-<功能名>.md`，功能名英文 kebab-case
- [ ] 产出文档中的 mermaid 图已全部通过本地渲染验证（spec-mermaid-diagram 验证脚本全部 VALID）
