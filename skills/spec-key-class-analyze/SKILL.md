# Spec 关键类分析

核心思想：从存量代码仓识别"牵一发而动全身"的关键类，产出一份关键类清单——回答"这个仓哪些类最重要、各自承担什么职责"。产出物刻意从简：只有一个 README、README 里只有一个表。

## 工作流程（三阶段，严格按序执行）

### 阶段 1：全仓扫描，识别关键类候选

按以下线索收集候选（兼顾多语言，按仓内实际技术栈取舍）：

- **入口直达类**：HTTP 路由 handler / RPC service 实现 / 消息订阅 handler / IDL 实现类直接调用的第一批业务类
- **高被引用类**：被多个模块 import / 引用（fan-in 高）的类——用 grep 统计类名在全仓的引用次数
- **核心领域模型**：承载业务状态与规则的 entity / model / domain 类，被多层共用
- **编排/服务类**：service / manager / coordinator / processor / engine 命名、串起多个协作类的类
- **状态与流程控制类**：状态机、工作流、生命周期管理、会话上下文类
- **全局中心类**：单例、注册表、工厂、调度中心类
- **排除项**：纯数据载体 DTO（无行为的 struct）、工具类、常量类、贫血模型（仅 getter/setter）、生成代码、测试代码——除非承载关键业务规则

### 阶段 2：关键性判定与筛选

逐候选判定是否"关键"，至少满足一条：

1. 处于核心调用链上（入口到核心逻辑的必经之路）
2. 承载关键业务规则或核心状态
3. 高 fan-in（被 ≥N 个模块依赖，N 按仓规模定，默认 3）
4. 是某功能域的协作中心（其他类围绕它协作）

规则：

- **不臆造关键性**：拿不准的宁可不收；未入选的候选在回复中简要说明原因（不写入 README），供人工复核
- **数量控制**：关键类贵在精不在多，单仓建议 10~30 个；超出说明筛选过宽，回到判定标准收紧
- 每个入选结论有代码证据（所在文件、调用方、数据结构），接口与唯一实现合并为一个条目（如 "BrowserService"）

### 阶段 3：生成清单

输出到代码仓 `docs/key-class/README.md`，**全文件只有一个表**：

- 表头固定：`| 类名 | 类的职责 |`
- 每个关键类一行，职责**不超过 38 个字**描述清楚（承担什么角色 + 为什么关键，凝练不堆砌，禁止抄类注释原文）
- 表前可用一行纯文本标注分析基准（分支 + 日期 + 类总数），除此之外不加任何表、图、章节

## 输出规范

- 归档文件：代码仓 `docs/key-class/README.md`（唯一产出文件，不产子文档、不分组、不画图）
- 全程中文输出
- 与其他 spec 产出互补：结构看 docs/structure/，入站接口看 docs/interface/，出站调用看 docs/external-call/，关键类看 docs/key-class/
- 更新策略：README 已存在时逐行对比更新（类被移除则删行、职责漂移则改行），不整表重写

## 质量检查清单

交付前逐项确认：

- [ ] 候选均经关键性判定，数量控制在 10~30 个，未入选者在回复中说明原因
- [ ] README 只有一个表，表头为 `类名 / 类的职责`
- [ ] 每条职责 ≤38 字，从代码证据归纳，无臆造
- [ ] DTO / 工具类 / 生成代码 / 测试代码未被误收为关键类
