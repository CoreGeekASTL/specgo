# Spec 业务逻辑完备性审核（多彩建模）

核心思想：把 Spec 文档翻译成多彩建模图（业务事件-角色-实体-描述的因果链路图），逻辑断裂点会在图上自然暴露；再用 ask-human 补齐断点，最终产出一份可供编码人员审核的 HTML。

## 工作流程（六阶段，严格按序执行）

### 阶段 1：解读文档，完成多彩建模

1. 通读用户提供的文档全文（Spec/需求/设计文档）。
2. 按 [references/color-modeling.md](references/color-modeling.md) 中的方法论提取四类元素：
   - 粉色「时刻/事件」：业务动作、状态变更、流程节点
   - 黄色「角色」：参与者（人、系统、外部服务）
   - 绿色「实体」：业务对象（人/地/物）
   - 蓝色「描述」：规则、约束、分类、属性说明
3. 按时序/因果箭头连接元素，形成完整建模链路。建模时不臆造文档中不存在的业务规则——不确定的内容标记为「待确认」，留到阶段 2 处理。

### 阶段 2：生成初版 HTML，检查逻辑断裂点，ask-human

1. 复制 [assets/model-template.html](assets/model-template.html) 为初版 HTML，将建模结果填入。
2. 对照 [references/gap-checklist.md](references/gap-checklist.md) 逐项检查逻辑断裂点与逻辑不全，在 HTML 中用红色虚线「断点卡片」高亮每一处。
3. **每发现一处断点，立即用交互提问工具 ask-human**，一次提问聚焦一个断点；提供 2-4 个具体候选答案选项（不允许"其他"类兜底选项由自己提供），并推荐最可能的一项。
4. 将用户的答复记录为断点的「人工裁定」，标注来源。

### 阶段 2.5：设计要素校验（功能设计文档必做，纯需求文档可跳过）

若被审文档是**功能设计文档**（含实现设计章节），在多彩建模校验之外，对照 gap-checklist.md 断点 10/11/12 逐项核对设计要素是否 ready：

1. **时序图**：功能设计章节是否采用时序图呈现，实现逻辑（基本流程+分支+异常）是否描述清楚
2. **验收用例**：是否具备功能验收用例（编号/前置条件/步骤/预期结果）
3. **接口信息**：外部接口（对外暴露）与跨服务调用接口是否明确到接口名/路径/输入输出

命中的缺项同样生成断点卡片、逐个 ask-human 补齐，流程与阶段 2 一致。

### 阶段 3：完善 HTML，清晰呈现建模结果

1. 把人工裁定回填到模型中，断点卡片转为「已补齐」状态（绿色边框 + 裁定内容）。
2. 完善 HTML 的可读性：
   - 四色图例置顶，非技术人员也能看懂
   - 因果链路按主流程→分支/异常流程分层排布
   - 每个元素卡片标注：所属颜色类别、原文出处（章节/段落）、确认状态（原文明确/人工补齐/仍存疑）
3. 仍存疑的项保留醒目标记，不得悄悄删除。

### 阶段 4：提醒编码人员审核

在最终回复中明确输出「编码人员审核提醒」，包含：
- HTML 文件位置与查看方式
- 审核要点清单：已补齐的断点裁定是否符合真实业务、仍存疑项、建模中缺失但编码时必须的细节（异常处理、并发、边界值）
- 明确提示：**HTML 未经编码人员确认前，不得进入编码阶段**

### 阶段 5：可选——按模板输出规范功能实现设计 md

审核完成后，**询问用户**是否按 [references/functional-design-template.md](references/functional-design-template.md) 输出一篇规范的功能实现设计 md。用户确认后：

1. 按模板章节结构生成：功能概述 / SR 设计 / 实现思路 / 实现设计（含用例时序图）/ 用户接口设计 / 实现接口设计 / 安全配置设计 / 功能规格 / DFX 分析 / 分配需求。
2. 内容来源=原文档已有内容 + 本次审核的人工裁定；实现设计章节的用例必须含时序图（mermaid sequenceDiagram），把补齐后的分支/异常流程画全。
3. 模板中的可选章节无对应内容时标注"不涉及"并裁剪；原文档与裁定都未覆盖的内容标"待确认"，**禁止脑补**。
4. 输出到原文档同目录，文件名 `<原文件名>-规范版.md`。

## 输出规范

- HTML 为单文件、无外部依赖，可直接在浏览器打开。
- HTML 生成后按网页交付规范保存版本，向用户提供可预览的版本；不要只给一个裸文件路径。
- 配色遵循多彩建模标准色，模板已内置，不要改动色板语义。
- 全程用中文输出建模内容与提问。
