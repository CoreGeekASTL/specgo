# spec-report — 代码生成收口总结报告

代码生成收口后的总结报告 skill。让人一眼看出：**任务是否都实现对了、用了哪些资产、用户怎么评价这次生成**。

## 报告结构（固定三节）

| 节 | 内容 | 事实来源 |
| --- | --- | --- |
| 一、代码生成的准确性 | 对照 develop-task 修改文件清单逐文件/函数核对：清单内是否全部实现、实现是否正确（对照 story 设计）、有无清单外改动；附测试用例执行结果 | develop-task + `git diff` + 验证命令实跑输出 |
| 二、资产使用情况 | 本次实现实际加载/使用了哪些资产文档，各自支撑了哪处实现 | story「外部文档引用」+ develop-task 引用表 + 实现期实际加载文档清单 |
| 三、用户反馈 | 询问用户：当前代码生成的准确率如何、当前的主要问题是什么 | 用户回答（不回答则整节不写入） |

## 何时触发

- 代码生成与测试完成后，用户要求收口总结："生成总结报告"、"spec-report"、"出交付报告"。
- 单独对某需求补出/重出报告（证据不足时复跑验证命令补证）。

## 输入

| 输入 | 来源 | 缺省处理 |
| --- | --- | --- |
| story 设计文档 + develop-task | 被分析仓 `docs/1-storys/{功能名}/` | 缺失则停止并提示先跑 spec-story-design |
| 代码变更 | `git diff`（已提交取本次需求 commit 范围，未提交取工作区） | 唯一事实来源 |
| 测试执行事实 | 验证命令实跑输出；单独触发时由本 skill 复跑取证 | 禁止凭"已通过"印象填写 |
| 资产使用清单 | story「外部文档引用」+ develop-task 引用 + 实现子代理返回的实际加载文档清单 | 逐条去重合并 |

**交互双模式（全局条款）**：第三节的用户询问**默认使用 ask-human 工具**；若任务开始时用户声明"以报告形式呈现"（或同类意思），则不使用 ask-human——问题随报告草稿一起输出，等用户回复后补写或确认跳过。

## 工作流程

### 第 1 步：取证（禁止凭印象）

1. **任务实现核对**：以 develop-task 修改文件清单为主键，逐文件对照 `git diff`——清单内未改、清单外改动都要显式暴露；再对照 story 设计逐条确认每处改动的实现与设计一致（接口契约/业务规则/数据模型口径）。
2. **测试执行结果**：收集或复跑验证命令实跑输出。DT 到测试函数级（逐函数 PASS/FAIL + 看护点），集成到用例步骤级（逐步骤结果 + 环境前置——数据基线/服务依赖/环境变量）。
3. **资产使用清单**：story「外部文档引用」+ develop-task 引用表 + 实现期实际加载文档清单，三方去重合并，逐条标注该资产支撑了哪处实现。

### 第 2 步：撰写第一、二节

按 references/report-template.md 填充：

1. **代码生成的准确性**：任务核对表四列——修改文件清单条目 / 实现状态（已实现/未实现/清单外）/ 正确性核对（符合设计/偏差说明）/ 证据（git diff 文件路径）；表后附测试用例执行结果（失败用例必须列出并附处理结论；前置不满足导致的失败显式标注）。
2. **资产使用情况**：表格三列——资产文档 / 应用了文档中的什么内容（≤30 字）/ 支撑的实现点；未使用任何资产、全靠读代码反推的实现点单独列出并标注「无资产支撑」。

### 第 3 步：用户反馈（第三节）

向用户提问两问（默认 ask-human，一次问完）：

1. 本次代码生成的准确率如何（如：百分之多少的改动无需返工）？
2. 当前代码生成的主要问题是什么？

- 用户回答 → 原话要点写入第三节（可整理措辞，不得改变意思）。
- 用户不回答/明确表示跳过 → **整节不写入报告**（模板中删除该节，不留空壳）。

### 第 4 步：落盘与收尾

- 落盘被分析仓 `docs/1-storys/{功能名}/{YYYYMMDD}-report.md`（与本需求 story/develop-task 同目录；次抛件带日期，同日同需求重跑同名覆盖；不改动 story/develop-task 本体）。
- 含 mermaid 代码块时，按 `<specgo插件目录>/skills/spec-analyze/references/mermaid-guide.md` 的「语法红线」逐图自查（本 skill 产出非资产文档，不跑验证脚本）。
- 返回中给出报告一句话结论：任务实现覆盖率、测试通过情况、资产使用篇数、用户反馈是否已收录。

## 输出模板

- references/report-template.md（元信息 + 三节固定结构，第三节按用户是否回答取舍）。

## 关键约束

- **基于实证**：任务核对/测试结果必须以 git diff、实跑输出与各步骤返回事实取证，逐文件逐用例落实，禁止臆造。
- **清单外显式暴露**：清单外改动、清单内未改都要列入并标注「清单外」/「未实现」。
- **用户反馈原话优先**：第三节内容来自用户回答，可整理措辞但不得代为编造；用户不回答则整节省略。
- **文档语言**：输出报告用中文，技术术语（DT / E2E / TTL 等）保留英文。

## 与其它 skill 的关系

- **spec-story-design / spec-code-generate**：本 skill 的上游，其产出（story、develop-task、实现与测试事实）是本 skill 的输入。
- **spec-analyze**：本体系产出的 docs/0-{域}/ 资产是第二节「资产使用情况」的统计对象。
- **mermaid 画图规则**：见 `<specgo插件目录>/skills/spec-analyze/references/mermaid-guide.md` 的「语法红线」（本 skill 产出非资产文档，只按红线自查，不跑验证脚本）。
