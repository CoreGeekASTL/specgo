# code-generate — 代码生成执行

依据 story 设计文档与 develop-task 修改文件清单，落地**完整、可运行、零 TODO** 的代码。

## 两条铁律（不可协商）

### 铁律一：完整代码，零 TODO

- 交付的每一个文件都必须是完整实现——函数体、分支、错误处理、边界条件全部写实。
- **禁止任何形式的占位**：`TODO`、`FIXME`、`// 待实现`、`// ...省略...`、`throw new Error("not implemented")`、`pass  # TODO` 等一律不允许出现。
- 自检：交付前全量搜索改动文件中的 `TODO|FIXME|XXX|HACK|待实现|省略|not implemented`，命中即返工。
- 写不出完整实现 = 输入不足（需求未明确/设计缺要素/存量代码事实不清），此时返回**待确认清单**结束本轮，由主代理向用户澄清后回传续做——**绝不**用 TODO 先糊弄过去。

### 铁律二：子代理执行

- 编码任务必须由子代理承担：编码需要同时装载 story、develop-task、引用资产文档与存量代码上下文，极易超出主代理上下文窗口。
- 主代理只负责派发（prompt 四要素）与验收，**绝不亲自编码**，也不"顺手补两行"。
- 子代理上下文仍不足时（文件过多），按修改文件清单**拆分为多个子代理**——按文件分组派发，每组输入只带该组文件所需的文档与代码上下文，主代理做组装与整体验收。

## 执行纪律（六步）

1. **加载输入文档（只读三波）**：story 设计文档（全读）+ develop-task（修改文件清单=编码唯一任务来源，验证方式=验收依据）+ 两文档**显式引用**的仓内文档；未引用的一律不读，禁止列目录找文档。
2. **定点核实存量代码**：只读"修改"类文件的改动点上下文（函数级）；"新增"类读文档指明的复用样板；其余代码一律不读。
3. **按清单实现**：修改文件清单逐文件落地，清单外不改；设计文档与存量代码冲突时以代码为准并列出偏差；需求未明确处返回待确认清单，不脑补。
4. **单元测试**：覆盖新增/改动逻辑，全部通过。测试代码同样适用铁律一（完整断言，禁止空用例占位）。
5. **集成测试**：代码仓存在集成/E2E 测试约定时（仓内测试目录，或 README/AGENTS.md 声明的集成测试方式）**必须主动运行**，不等用户提醒；不存在则跳过并在返回中注明。
6. **验证**：运行 develop-task「验证方式」章节的命令（构建/测试），失败修复重跑；未跑过验证命令不得宣称完成。

## 返回格式

生成/修改文件清单 + 冲突偏差 + 零 TODO 自检结果（搜索命令与命中数=0）+ 验证命令结果（DT 到测试函数级：逐函数 PASS/FAIL）+ 集成测试结果（到用例步骤级：逐步骤结果与环境前置）+ **实际加载的文档清单**（story/develop-task/显式引用的仓内文档，逐条带路径，供报告环节取证）。

## 红线

| 想法 | 现实 |
|---|---|
| "这里先 TODO，回头补" | 零 TODO 是交付红线——写不出完整实现就返回待确认清单 |
| "改动小，主代理顺手写了" | 编码一律子代理执行，主代理只派发与验收 |
| "一个子代理塞不下就精简输入" | 按文件分组拆多个子代理，不砍必要上下文 |
| "测试写个空用例占位" | 测试与实现同标准——完整断言，禁止占位 |
| "集成测试等用户提醒再跑" | 仓里有集成/E2E 测试就必须主动运行 |
| "代码写完就算完成" | develop-task 验证命令实跑通过才算完成 |
