# 代码仓交互模型分析 Skill（arch-interaction-model-analyze）

## 目的

从存量代码仓提取业务流程的**交互模型**资产——每条流程回答两个问题：

1. 这条业务流程的主链路穿过哪些模块与外部参与方？
2. 参与方之间的消息走向（调用次序与内容）是怎样的？

产出：UML 时序图（mermaid）+ 参与方说明 + 补充说明，落盘被分析仓的 `docs/0-arch/interaction-model/interaction-model-{flow}.md`，**每业务流程 1 篇**。

与结构模型（arch-structure-model-analyze）的关系：结构模型回答"模块之间的静态依赖方向"，交互模型回答"一条业务流程在模块之间的动态消息走向"，两者互补，同归 `docs/0-arch/`。

**只画主链路**：时序图只承载主流程（happy path）的消息序列。分支条件、异常处理、重试/拒绝/补偿等逻辑**不画入图、不在本文档展开**——它们归业务规则资产（biz-rules-analyze，`docs/0-biz/rules/`）承载；该资产未建时在补充说明末尾注明"分支逻辑归业务规则资产，待补"。

两种运行模式：**单流程模式**（用户点名流程，只梳理该流程）与**全量模式**（用户未指明流程时的默认模式——枚举仓内全部业务入口，逐流程产出文档，不再询问"梳理哪个"）。全量模式的"枚举"只扫入口注册点（路由注册/订阅注册/定时任务注册/IDL 契约），不做全仓通读；每条流程的证据来源仍是该流程实际经过的代码文件。

**自包含原则**：本 skill 所需模板归档在自身 references/ 目录下，不依赖其它 skill 的文件。

## 何时触发

- 用户指定某个业务流程，要求"梳理流程"、"画时序图/调用链"、"整理流程文档"、"XX 流程是怎么走的"——单流程模式。
- 用户未指明流程、或要求"梳理全部业务流程"、"把所有流程落成文档"——全量模式（默认梳理全部流程，见第 1 步），**不得阻塞式询问**。
- 用户要求补充某条业务链路的交互模型资产。

## 工作流程

按下述步骤顺序执行。分析基于**实际读到的代码**，不得臆测；读不到就明确标注"未识别（原因：xxx）"。

### 第 1 步：确定梳理范围

1. **用户指明流程名 → 单流程模式**：只梳理该流程。流程名含糊时（如"登录流程"但仓内有多种登录），列出候选让用户选择。
2. **用户未指明流程 → 全量模式（默认）**：枚举仓内全部业务流程，逐流程执行第 2~6 步，**不得询问"要梳理哪个流程"**。
3. **枚举口径（全量模式）**：只扫入口注册点——HTTP 路由注册、消息订阅注册、定时任务注册、IDL 契约实现；按入口 handler 粒度识别流程，一个 handler 对应一条主链路、一篇文档。测试/调试/健康检查类入口不算业务流程，直接排除，排除清单在最终汇总中交代。
4. **流程边界**：起点（什么触发）与终点（什么算走完）。单流程模式下用户未说明时给出你的推断并向用户确认；全量模式下按实读代码自行界定，不逐条确认。

### 第 2 步：定位入口，顺链阅读代码

1. 从流程入口切入：HTTP 路由注册、消息订阅 handler、定时任务、IDL 契约实现等，定位入口文件与函数。
2. 顺调用链逐层阅读（controllers → service → dao → models，或本仓等价分层），只读与本流程直接相关的代码，**禁止全仓通读**（全量模式的入口枚举只读注册/配置类文件，不在此限）。
3. 沿途记录：**主链路上的消息序列**（谁调谁、传递什么）、每个参与方归属的模块、读写哪些实体/缓存/文件、发生哪些外部调用（下游服务/消息队列）、关键代码位置（文件路径，不带行号）。
4. 分支与异常路径只需识别"主链路在哪一步可能岔出去"，**不深入追分支内部**——分支细节是业务规则资产的事。
5. 用户给的入口线索与实读链路不符时（线索文件不在主链路上，如管理面/运维面代码），以实读代码为准，在补充说明中一句话切割，不强行入图。
5. 可借助存量资产加速：`docs/0-arch/structure-model/`（结构模型，模块归属判定）、docs/0-tech/external-call-guidelines/（下游契约）、`docs/1-storys/`（既有 story 设计文档）。资产缺失不影响本流程梳理，以实读代码为准。

### 第 3 步：确定参与方粒度

时序图的 participant 只放**跨边界的交互方**：

- 本仓**模块**（对齐结构模型的模块划分，取第一层目录/包粒度）；
- 外部参与方：流程触发者（终端/调用方）、下游服务、中间件（DB/缓存/MQ）。

边界判定：participant 必须是数据或控制流**跨出模块内存边界**的交互方。模块内的进程内组件（模块内缓存 map、模块内工具类）不算参与方，归入所属模块；嵌入式存储（如 SQLite）虽无独立部署，但数据经 SQL 边界落盘，可作为中间件参与方单列，其"代码位置"填仓内访问/建表文件。

模块内部的类间调用**不展开**（模块内消息不画）。退化情形：主链路全部集中在单一模块内时，允许下钻到该模块内的关键类作为 participant，并在补充说明中注明下钻理由。

运行时方差（缓存命中短路、快速路径）**不属于业务分支**：主链路画完整路径（如未命中→回源），方差行为在补充说明中一句话交代。

participant 显示名用模块名/外部方名，participant 对应的代码位置（文件路径）放入「参与方说明」表。

### 第 4 步：按模板产出交互模型文档

按 ../assets/interaction-model--interaction-model-template.md 的骨架产出（概述 + 主链路时序图 + 参与方说明 + 补充说明）：

1. **概述**：业务目标、触发者、参与模块，1~3 句。
2. **主链路时序图**：一张 mermaid `sequenceDiagram` 表达完整主链路的消息走向。同步返回用 `-->>`，异步消息用 `->>` 并在补充说明点明；不画 alt/opt/loop 等分支块。
3. **参与方说明表**：参与方 / 类型（模块/外部触发者/下游服务/中间件）/ 代码位置（文件路径，不带行号）/ 本流程中的职责。
4. **补充说明**：2~4 句，点明关键步骤的业务含义与涉及的关键实体状态变更；有缓存短路等运行时方差时一句话交代；末尾一行交代分支逻辑归属（业务规则资产，已建则给链接，未建注明"待补"）。

规则：

- 时序图必须与代码实际调用链一致，禁止臆造消息；每条消息对应真实存在的调用。
- 只画主链路：图中出现 alt/opt/分支边即视为违规，退回重画。
- 涉及下游调用时，引用 docs/0-tech/external-call-guidelines/ 存在的文档链接，无则注明"无出站调用文档，待核实"。
- 所有内容必须有代码事实依据；代码中读不出来、属于业务规约的内容标注"代码未体现，待确认"，禁止脑补。

### 第 5 步：落盘 docs/0-arch/interaction-model/

- 输出到**被分析代码仓根目录**的 `docs/0-arch/interaction-model/interaction-model-{flow}.md`；目录不存在则创建（连同 `docs/` 一起创建）。
- `{flow}` 实例 slug **从代码标识符派生**：取流程入口的代码标识符（入口 handler 函数名 / 路由末段 / 消息 topic 名）转 kebab-case，如 `login`、`check-auth`；禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。用户确认的流程中文名只进文档标题，不进文件名。
- 同名文件已存在**直接覆盖更新**——模型文档是活文档，固定名、覆盖更新，git diff 即演进史。
- **资产主文档 `README.md` 必产出**：同目录落 `README.md`（活文档，同名覆盖），内容仅两项——元信息表（分支/更新日期/Skill）+ 流程导航表（流程名 → `interaction-model-{flow}.md` 链接 + 一句话流程说明，从各文档首行标题提取）；单流程模式（用户指明流程）时同样刷新该 README，只增改对应行。
- 索引分工：本资产目录的 `README.md` 由本 skill 产出；域索引 `docs/0-arch/README.md` 与总索引 `docs/README.md` 自 v3.0 起不再自动生成（spec-index 已移除），本 skill 不维护。

### 第 6 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块，交付前必须运行 mermaid 本地验证脚本逐文件校验：

```bash

```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。

- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 `<specgo插件目录>/skills/spec-analyze/references/mermaid-guide.md` 的「语法红线」。
- 全量模式：全部产出文档一次性传入校验；全部 VALID 后在回复中给出汇总——流程清单（流程名 → 文档路径）与排除入口清单（入口 + 排除理由）。

## 输出模板

严格按 ../assets/interaction-model--interaction-model-template.md 骨架填充——只填占位符、表格行、图；写作规则见上文各步骤与「关键约束」。

## 关键约束

- **通用性**：本 skill 不依赖任何特定代码仓的结构。执行时基于实际探测结果走，禁止凭仓库名或已知项目结构臆测。
- **全量模式默认**：用户未指明流程时默认枚举全部业务流程逐篇产出，禁止以"先确认范围"、"先问清流程"为由阻塞；排除入口仅限测试/调试/健康检查类，且排除清单必须在最终汇总中交代。
- **基于实证**：所有消息走向、参与方职责结论必须有代码支撑，证据形式为 `文件路径`，**不得出现代码行号**，行号会随代码变更失效且无跨工具稳定性。
- **只画主链路**：分支条件、异常处理不画入图、不展开——归业务规则资产（biz-rules-analyze）承载。图中出现 alt/opt/loop 分支块即违规。
- **参与方模块粒度**：participant 取模块与跨内存边界的外部参与方，模块内类间调用与进程内组件不展开；单模块退化情形允许下钻关键类并注明理由。
- **只读不改**：只读、只分析、只产出文档，不改动被分析代码仓的任何文件（新建 `docs/0-arch/interaction-model/` 目录和文档文件除外）。
- **语言无关**：不预设被分析仓的语言，按实际探测结果走。
- **实例 slug 从代码标识符派生**：`{flow}` 取流程入口代码标识符转 kebab-case，禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。
- **活文档覆盖更新**：`docs/0-arch/interaction-model/` 下模型文档同名直接覆盖，不保留历史副本、不加日期后缀——差距报告才带日期，模型文档不带。
- **成品纯净**：最终文档只含成品内容（标题、概述、图、表格、补充说明）。模板顶部的元说明、写作指令行、占位符说明均为规则，不复制进成品。第 1~2 步的探测过程（执行的 grep/rg 命令、命中输出摘要）仅供自检，绝不写入最终文档——其结论须以 `文件路径` 证据形式进入相关表格，且**证据不得含代码行号**。
- **文档语言**：输出文档用中文，技术术语（Controller / Service / Repository / Module 等）保留英文。
