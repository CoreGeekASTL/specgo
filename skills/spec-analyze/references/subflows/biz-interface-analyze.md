# 代码仓对外接口分析 Skill（biz-interface-analyze）

## 目的

从存量代码仓提取**接口**资产——本仓对外提供的接口清单（服务自己暴露给外部调用的入口），按功能域聚类，回答两个问题：

1. 本仓对外提供哪些接口（HTTP 路由 / RPC service / 消息订阅 handler / 定时任务 / IDL 契约）？
2. 这些接口按业务功能如何聚类，每个接口的请求与响应数据结构是什么？

产出：**一个主文档 + 多个子文档**，落盘被分析仓的 `docs/0-biz/interface/`：

- 主文档 `README.md`：元信息 + 接口全景（功能域索引导航表）；
- 子文档 `interface-{feature}.md`：每个功能域 1 篇，含定位 + 接口表格 + 表下逐接口数据结构说明。

> 注意：本 skill 的"对外接口"= 本仓作为服务端暴露给外部调用的入口，**不是**本仓调用别人的接口（那是消费侧，归外部调用/通信规范资产）。仓内模块间的语言级 interface 契约不算对外接口，不纳入。

**自包含原则**：本 skill 所需模板与脚本归档在自身 references/ 与 scripts/ 目录下，不依赖其它 skill 目录或插件 templates/ 目录的文件。

## 何时触发

- 需要盘点代码仓对外提供哪些接口、梳理对外接口清单时。
- 需要按业务功能给接口分组、补充接口的请求/响应数据结构说明时。
- 需要为接口治理、接口文档、新人上手沉淀接口资产时。
- 典型触发语："代码仓对外提供什么接口""对外接口""外部接口""服务暴露的接口""接口清单""接口盘点""接口文档"。

## 工作流程

按下述步骤顺序执行。分析基于**实际读到的代码与扫描结果**，不得臆测。

### 第 1 步：明确范围与排除目录

- 确认代码仓路径、主要语言、Web 框架（Beego/gin/Spring/FastAPI 等）。
- 确认排除目录（生成代码、第三方 vendor）。默认排除：`vendor/` `node_modules/` `third_party/` `*_gen/` `*.pb.go` 等；测试目录**默认纳入**（测试中的路由/订阅也列出，标注"仅测试使用"）。
- 确认是否包含消息订阅/定时任务入口：默认包含（异步入口也是对外提供的服务能力）。

### 第 2 步：扫描对外接口注册点

两条线并行，再交叉核对：

1. **IDL/契约文件**：查找 `*.proto`、`*.thrift`、`*.graphql`、OpenAPI/Swagger `*.yaml` 等接口契约文件，提取 service/rpc/path 定义。
2. **代码扫描**：运行内置扫描脚本：

```bash
python3 <skill_dir>/../assets/interface--scan_interfaces.py <repo_path> -o scan_result.md
# 可选：--lang go|java|cpp|python 限定语言；--format json 结构化结果
```

脚本扫描三类对外接口注册点：
- **IDL/契约类**：proto service/rpc、thrift service、OpenAPI paths、GraphQL Query/Mutation/Subscription
- **框架路由类**：HTTP/RPC 入口注册点（Beego/gin/echo/chi、grpc Register、net/http HandleFunc、Spring MVC 注解、Dubbo、FastAPI/Flask/Django、C/C++ 注册表、自封装 RouteMapping）
- **消息/事件订阅类**：MQ 消费订阅、事件注册、定时任务入口

3. **交叉核对**：IDL 契约与代码实现交叉核对——有契约无实现=未落地；有实现无契约=自研隐式接口。注意"易遗漏项"（IDL 生成代码虚增、同接口多实现、消息/事件订阅未走显式定义、宏/表驱动注册、网关透传、Beego 注解路由、自封装路由表、已下线接口）。详见 ../assets/interface--interface-catalog.md。
4. **按功能域聚类**：将扫描到的接口按业务功能聚类（如"用户认证""白名单管理""配置同步"），**禁止按技术层命名**（如"controller 层"）。聚类依据按优先级：路由路径前缀 → controller/service 归属 → IDL service 分组 → 业务语义相近。每功能域一般 2~10 个接口；超过 10 个考虑拆分；只有 1 个接口且语义独立时允许单独成功能域。

### 第 3 步：产出主文档 + 各功能域子文档

产出结构如下，落盘被分析仓的 `docs/0-biz/interface/`（目录不存在则创建，连同 `docs/` 一起创建）：

```
<repo>/docs/0-biz/interface/
├── README.md                  # 主文档：元信息 + 接口全景（功能域索引导航表）
├── interface-{feature1}.md    # 子文档：该功能域的定位 + 接口表 + 表下数据结构
├── interface-{feature2}.md
└── ...
```

**命名规则**：

- 主文档：`README.md`（目录索引惯例）。
- 子文档：`interface-{feature}.md`，`{feature}` 实例 slug **从代码标识符派生**——取该功能域的代表性代码标识符（主 controller/handler 名、路由路径前缀、IDL service 名）转 kebab-case（如 `interface-login.md`、`interface-file-mgmt.md`），禁止 AI 自由起名，保证重跑产出同名文件、资产不断代；功能域中文名只进文档标题与索引表，不进文件名。

**主文档 `README.md`** 按 ../assets/interface--readme-template.md 填充：固定三行元信息表（分支/更新日期/Skill）+ 接口全景索引表（功能域 | 接口数 | 子文档链接，无死链）。README 只起导航作用，不加其他章节；探测到但无法归入任何功能域的接口，在索引表下方一行逐条列出并说明原因。

**子文档 `interface-{feature}.md`** 按 ../assets/interface--subdoc-template.md 填充（每个功能域一份）：

1. 元信息（功能名、接口数、所属 server 外部/内部）+ 返回主文档链接
2. **定位**：一句话说明该功能解决什么业务问题
3. **接口表格**：列含 接口名 | 作用 | 所在文件 | 方法/路径（HTTP 填 `POST /api/v1/xxx`，RPC 填 `UserService.GetUser`，消息订阅填 `Consume topic-xxx`，定时任务填 cron 表达式）
4. **表格下方逐个接口的数据结构说明**：针对接口表格里的每个接口，说明其请求与响应数据结构（结构名 + 定义位置 + 关键字段+约束），同功能内多接口共用的结构只在首次出现处详述，后续注明"同上"

**人类友好硬性要求**：

- 每个功能域一个子文档，**按业务功能命名**，禁止按技术层命名。
- 接口必须用**表格**列出（接口名/作用/所在文件/方法或路径），禁止散文段落描述单个接口。
- **"所在文件"列只填文件路径，不带行号**（如 `controllers/login_controller.go`）；全文证据锚点同样只写文件路径，不带行号。
- 每个接口的请求/响应数据结构**写在接口表格下方**，逐个接口说明，不要把所有数据结构堆成一张孤立的大表。
- 数据结构只列关键字段与约束，不整段搬运 struct 定义；超过 8 字段只列关键。
- 主文档功能域索引表每行带子文档链接，可从总览直跳详情；子文档元信息带返回主文档链接。
- 单功能域接口数 > 10 时，列代表性 5~10 处并注明"全量见 xxx"，禁止全量罗列刷屏。

**更新策略**：`docs/0-biz/interface/` 下文档已存在时按功能域逐篇对比更新（功能已下线则标注"已下线"并保留子文档灰显，或从索引移除并归档）；主文档索引随功能增删同步更新。同名文件**直接覆盖更新**——接口文档是活文档，固定名、覆盖更新，git diff 即演进史。本 skill 不维护域索引：`docs/0-biz/README.md` 域索引与总索引由 spec-index 统一生成。

### 第 4 步：输出后自检（防漏文件、防臆造）

文档产出后、交付前必须执行差集自检。漏文件的根因通常是"扫描到了但归类时丢了"，靠通读复查很难发现，必须用清单比对：

1. **生成全量清单 A**：从第 2 步扫描结果（scan_result）提取全部接口标识（HTTP 填 `方法+路径`，RPC 填 `Service.Method`，消息订阅填 topic，定时任务填 cron）。
2. **生成已记录清单 B**：从已产出的各子文档接口表格 + README"未归类接口"节提取全部接口标识。
3. **差集比对**：
   - **A − B（漏记）**：逐个处理——补入对应功能域子文档，或写入 README"未归类接口"并说明理由。禁止静默丢弃。
   - **B − A（多出）**：逐条核实——是动态注册/宏展开等扫描盲区（保留并注明依据），还是臆造（删除）。
4. **文件维度反查**：列出第 2 步命中过注册点模式的全部源码文件，确认每个文件至少被一个功能域子文档的"所在文件"列引用；未被引用的文件逐个追查——要么有接口漏记，要么在自检结论里写明该文件无对外接口的理由（如纯内部 helper）。
5. **自检结论写入 README**：在功能域索引表后加一行自检结论，格式：`自检：扫描 N 个接口，已记录 N 个，未归类 M 个（见上表），差集已清零（YYYY-MM-DD）`。差集未清零的禁止交付。

### 第 5 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块（接口全景图等），交付前必须运行 mermaid-validate skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/mermaid-validate/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 mermaid-validate skill 的「语法红线」。

## 输出模板

严格按以下模板骨架填充——只填占位符、表格行；写作规则见上文各步骤与「关键约束」。

- 主文档：../assets/interface--readme-template.md（元信息 + 接口全景索引表）
- 子文档：../assets/interface--subdoc-template.md（元信息 + 定位 + 接口清单表 + 数据结构说明）

## 关键约束

- **语言无关**：本 skill 不依赖任何特定代码仓的结构、语言或框架，执行时基于实际探测结果走，禁止凭仓库名或已知项目结构臆测。
- **基于实证**：所有接口记录必须有代码/契约支撑，证据形式为文件路径，**不带行号**（行号随代码变更失效且无跨工具稳定性）；"所在文件"列与数据结构"定义位置"同样只写文件路径。
- **实例 slug 从代码标识符派生**：`{feature}` 取功能域代表性代码标识符（主 controller/handler 名、路由前缀、IDL service 名）转 kebab-case，禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。
- **活文档覆盖更新**：`docs/0-biz/interface/` 下文档同名直接覆盖，不保留历史副本、不加日期后缀。
- **只读不改**：只读、只分析、只产出文档，不改动被分析代码仓的任何文件（新建 `docs/` 下产出目录与文档文件除外）。
- **成品纯净**：最终文档只含成品内容（标题、元信息、表格、数据结构说明）。扫描结果（scan_result）、grep 命中清单等探测过程产物仅供自检，绝不写入最终文档——其结论以文件路径证据形式进入接口表格。
- **差集清零才交付**：第 4 步自检的扫描清单与文档清单差集必须清零，命中注册点的源码文件均被功能域引用，自检结论写入 README 后才允许交付。
- **三类全覆盖**：IDL 契约/框架路由/消息订阅三类全部排查过，未命中类目须确认"确实没有"而非"没找到"；IDL 契约与代码实现交叉核对，生成代码不虚增接口统计；同接口多实现全部列出并标注选择机制。
- **功能域按业务命名**：无"controller 层""service 层"等技术层命名。
- **文档语言**：输出文档用中文，技术术语（Controller / Service / RPC / IDL / handler 等）保留英文。
