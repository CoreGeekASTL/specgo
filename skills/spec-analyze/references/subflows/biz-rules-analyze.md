# 代码仓业务规则提取 Skill（biz-rules-analyze）

## 目的

从存量代码仓提取**业务规则**资产——散落在分支判断、参数校验、状态迁移里的业务逻辑，把它从代码里"捞"出来变成可查阅的规则条目。每条规则回答三个问题：

1. 什么条件下触发（条件）？
2. 触发后发生什么（动作：拒绝/返回错误码/状态迁移/回滚等）？
3. 依据在哪里（代码文件）？

产出：按需求类（功能域）整理"条件 → 动作 + 依据"规则条目表格，落盘被分析仓的 `docs/0-biz/rules/rules-{feature}.md`，**每需求类 1 篇**。产出为纯表格文档，不含 mermaid 图。

与交互模型（arch-interaction-model-analyze）的关系：交互模型只画主链路（happy path），**分支与异常逻辑不画入图、不在交互模型文档展开，归本资产承载**；交互模型文档末尾指向 `docs/0-biz/rules/`。两者互补——交互模型回答"主流程怎么走"，业务规则回答"每一步可能怎么岔出去、岔出去后发生什么"。

两种运行模式：**单域模式**（用户点名功能域，只提取该域）与**全量模式**（用户未指明时的默认模式——以对外入口注册点归集功能域，逐域产出，不再询问"提取哪个域"）。全量模式的"枚举"只扫入口注册点，不做全仓通读；每条规则的证据来源仍是该规则实际所在的代码文件。

**自包含原则**：本 skill 所需模板归档在自身 references/ 目录下，不依赖其它 skill 的文件。

## 何时触发

- 用户指定某个功能域，要求"梳理规则"、"提取分支/校验逻辑"、"整理错误码/状态迁移规则"——单域模式。
- 用户未指明功能域、或要求"提取全部业务规则"、"把分支逻辑都落成文档"——全量模式（默认，见第 1 步），**不得阻塞式询问**。
- 交互模型梳理完成后，补充其末尾指向的分支与异常逻辑资产。

## 工作流程

按下述步骤顺序执行。分析基于**实际读到的代码**，不得臆测；读不到就明确标注"未识别（原因：xxx）"。

### 第 1 步：确定梳理范围

1. **用户指明功能域 → 单域模式**：只提取该功能域。域名含糊时（如"登录"但仓内有多种登录），列出候选让用户选择。
2. **用户未指明功能域 → 全量模式（默认）**：枚举仓内全部对外入口，按功能域聚类后逐域执行第 2~4 步，**不得询问"要提取哪个域"**。
3. **枚举口径（全量模式）**：只扫入口注册点——HTTP 路由注册、消息订阅注册、定时任务注册、IDL 契约实现；不做全仓通读。测试/调试/健康检查类入口不算业务功能域，直接排除，排除清单在最终汇总中交代。
4. **功能域聚类**：将入口按业务功能归集为功能域（即"需求类"）。聚类依据按优先级：路由路径前缀 → 入口 handler/controller 归属 → IDL service 分组 → 业务语义相近。禁止按技术层命名（如"controller 层"）。`{feature}` slug 取功能域内入口的公共代码标识符（路由前缀 / controller 名 / IDL service 名）转 kebab-case。

### 第 2 步：定位入口，顺链阅读代码

1. 从功能域入口切入：HTTP 路由注册、消息订阅 handler、定时任务、IDL 契约实现等，定位入口文件与函数。
2. 顺调用链逐层阅读（controllers → service → dao → models，或本仓等价分层），只读与本功能域直接相关的代码，**禁止全仓通读**（全量模式的入口枚举只读注册/配置类文件，不在此限）。
3. 沿途识别**规则点**，共六类：
   - **条件分支**：if/switch 中有业务语义的判断（资格判断、黑白名单、重复提交、配额判断等）；
   - **参数与格式校验**：必填、取值范围、格式、合法性校验；
   - **状态机迁移**：状态字段的合法迁移集合与迁移条件（如订单状态 `Pending → Paid`）；
   - **阈值常量**：有业务含义的上限/下限/次数/时长常量（重试上限、有效期、限额）；
   - **错误码返回**：错误码与触发条件的映射；
   - **事务与回滚条件**：开启/提交/回滚事务的判定条件。
4. 只收录**有业务语义**的规则点。纯技术防御代码（nil 判断、类型断言、序列化失败、框架层 bind 失败等无业务含义分支）不收录——除非它产生业务可见行为（如返回特定业务错误码）。
5. 沿途记录每条规则点：触发条件（含关键表达式/常量名/错误码名/枚举值）、条件成立后的动作、所在文件路径（不带行号）、服务的来源入口。
6. 可借助存量资产加速：`docs/0-biz/interface/`（接口资产，功能域归集参照）、`docs/0-arch/interaction-model/`（交互模型，主链路与分叉点定位）、`docs/1-storys/`（既有 story 设计文档）。资产缺失不影响规则提取，以实读代码为准。

### 第 3 步：整理规则条目

1. **每规则一行**，五列：`| 规则名 | 条件 | 动作 | 依据 | 来源入口 |`。
2. **规则名 slug 从代码标识符派生**：取承载规则的代码标识符（函数名/常量名/错误码名/状态枚举名）转 kebab-case，如 `check-white-list`（函数 `CheckWhiteList`）、`max-login-retry`（常量 `MaxLoginRetry`）、`err-invalid-param`（错误码 `ErrInvalidParam`）；禁止 AI 自由起名。同一标识符拆出多条规则时加短后缀区分（如 `-empty`、`-format`）。规则名在同一篇文档内唯一。
3. **条件**：用业务语言描述触发条件，保留关键代码表达式/常量名/枚举值（如"连续失败次数 ≥ `MaxLoginRetry`"、"订单状态为 `Pending` 且支付回调成功"）。
4. **动作**：条件成立后的业务后果——返回错误码、拒绝请求、状态迁移、锁定、回滚、降级等，写清后果而非只写"返回错误"。
5. **依据**：文件路径，不带行号；一条规则跨多个文件时用 `；` 分隔全部列出。
6. **来源入口**：该规则服务的对外入口（HTTP 填 `方法 + 路径`，消息订阅填 `Consume topic-xxx`，定时任务填 cron 表达式）；同一规则被多个入口共用时只列一行、来源入口逐条列全。
7. 表内规则按链路先后顺序或规则点类型聚组排列，便于顺读；规则条数过多时（>30）优先保留有业务后果的规则，并在补充说明交代取舍口径。

### 第 4 步：按模板产出规则文档并落盘

按 ../assets/rules--rules-template.md 的骨架产出（概述 + 规则表 + 补充说明）：

1. **概述**：1~3 句，该功能域解决什么业务问题、规则提取自哪些入口链路、覆盖哪几类规则点。
2. **规则表**：第 3 步整理的规则条目。
3. **补充说明**：2~4 句，点明规则之间的优先级/互斥关系——校验执行顺序、先拦哪个后拦哪个、状态迁移是否可逆、是否存在短路规则；有跨入口共用规则时一句话交代。

落盘规则：

- 输出到**被分析代码仓根目录**的 `docs/0-biz/rules/rules-{feature}.md`；目录不存在则创建（连同 `docs/` 一起创建）。
- 同名文件已存在**直接覆盖更新**——规则文档是活文档，固定名、覆盖更新，git diff 即演进史。
- **资产主文档 `README.md` 必产出**：同目录落 `README.md`（活文档，同名覆盖），内容仅两项——元信息表（分支/更新日期/Skill）+ 功能域导航表（功能域 → `rules-{feature}.md` 链接 + 规则条目数 + 一句话说明，从各文档首行标题提取）；单功能域模式（用户指明功能域）时同样刷新该 README，只增改对应行。
- 索引分工：本资产目录的 `README.md` 由本 skill 产出；域索引 `docs/0-biz/README.md` 与总索引 `docs/README.md` 自 v3.0 起不再自动生成（spec-index 已移除），本 skill 不维护。

### 第 5 步：收尾汇总（全量模式）

全部功能域产出后，在回复中给出汇总：功能域清单（功能域 → 文档路径）、排除入口清单（入口 + 排除理由）。汇总只进回复，不写入产出文档。

## 输出模板

严格按 ../assets/rules--rules-template.md 骨架填充——只填占位符与表格行；写作规则见上文各步骤与「关键约束」。

## 关键约束

- **通用性**：本 skill 不依赖任何特定代码仓的结构。执行时基于实际探测结果走，禁止凭仓库名或已知项目结构臆测。
- **全量模式默认**：用户未指明功能域时默认枚举全部功能域逐篇产出，禁止以"先确认范围"、"先问清功能域"为由阻塞；排除入口仅限测试/调试/健康检查类，且排除清单必须在最终汇总中交代。
- **基于实证**：所有规则条目的条件、动作、来源入口必须有代码支撑，证据形式为 `文件路径`，**不得出现代码行号**，行号会随代码变更失效且无跨工具稳定性。代码中读不出来、属于业务规约的内容标注"代码未体现，待确认"，禁止脑补。
- **只收录业务规则**：纯技术防御代码（nil 判断、类型断言、序列化失败等无业务语义分支）不入表，除非产生业务可见行为。
- **只读不改**：只读、只分析、只产出文档，不改动被分析代码仓的任何文件（新建 `docs/0-biz/rules/` 目录和文档文件除外）。
- **语言无关**：不预设被分析仓的语言/框架，按实际探测结果走。
- **实例 slug 从代码标识符派生**：`{feature}` 取功能域内入口的公共代码标识符（路由前缀/controller 名/IDL service 名）转 kebab-case；规则名取承载规则的函数名/常量名/错误码名/状态枚举名转 kebab-case。禁止 AI 自由起名，保证重跑产出同名文件、资产不断代。
- **活文档覆盖更新**：`docs/0-biz/rules/` 下规则文档同名直接覆盖，不保留历史副本、不加日期后缀。
- **成品纯净**：最终文档只含成品内容（标题、概述、规则表、补充说明）。模板顶部的元说明、写作指令行、占位符说明均为规则，不复制进成品。探测过程（执行的 grep/rg 命令、命中输出摘要）仅供自检，绝不写入最终文档——其结论须以 `文件路径` 证据形式进入规则表，且**证据不得含代码行号**。
- **文档语言**：输出文档用中文，技术术语（Controller / Service / DAO / HTTP / topic 等）保留英文。
