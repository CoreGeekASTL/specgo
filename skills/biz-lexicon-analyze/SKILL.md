# 领域词典分析 Skill（biz-lexicon-analyze）

## 目的

输入一个存量代码仓路径，提取**领域词典**资产——业务与代码共用的受控词汇集，回答三个问题：

1. 这个代码仓的业务领域有哪些受控术语（业务概念、实体、状态、错误码等）？
2. 每个术语的释义与语境边界是什么（同名异义时逐语境一条）？
3. 每个术语在代码里叫什么（代码标识符 + 文件路径）？

产出：**按业务子域拆分的多篇文档**——主文档 `lexicon.md`（元信息 + 说明 + 全仓待确认清单 + 子域导航 + 「通用」节词条）+ 每功能域 1 篇 `lexicon-{子域锚点}.md`（仅该域四类词条表）。组织口径保持「**子域 × 术语类型**」两级：一级按代码功能域拆分子域文档（外加主文档内固定的「通用」节），每个子域文档内再按四类受控术语类型分组小节：

| 术语类型 | 来源映射 | 内涵 |
| --- | --- | --- |
| 实体与业务概念 | 来源 1（接口/请求响应模型）+ 来源 2（DB 实体） | 业务对象、字段概念、领域名词 |
| 常量与状态枚举 | 来源 5（常量定义） | 类型常量、状态机枚举、业务开关 |
| 错误码 | 来源 4（错误码定义） | 返回码、错误变量（业务异常概念） |
| 事件 | 来源 3（事件模型） | 事件类型、事件字段、topic |

落盘被分析仓根目录的 `docs/biz/lexicon/`（不存在则创建，连同 `docs/` 一起创建）。某子域没有某类术语时省略该类型小节；「通用」节在主文档内同样按四类分组。

词典是其它 biz 资产（接口 / 对象模型 / 数据模型 / 业务规则）的词汇基线：那些文档里出现的业务名词，应能在本词典查到释义与代码命名映射。

**自包含原则**：本 skill 所需模板归档在自身 references/ 目录下，不依赖其它 skill 目录或插件 templates/ 目录的文件。

## 何时触发

- 需要统一业务与代码的术语口径、沉淀受控词汇时。
- 新人上手 / 需求评审 / AI 编码需要名词解释与代码命名映射时。
- 同名异义、同义异名已造成沟通或实现歧义，需要梳理时。
- 典型触发语："领域词典""术语表""词汇表""统一语言""术语口径""名词解释""lexicon""glossary""ubiquitous language"。

## 工作流程

按下述步骤顺序执行。分析基于**实际读到的代码与注释**，不得臆测。

### 第 1 步：明确范围与排除目录

- 确认代码仓路径、主要语言。排除生成代码与第三方目录：`vendor/` `node_modules/` `third_party/` `*_gen/` `*.pb.go` 等——IDL 生成代码的字段注释可作释义证据，但代码命名映射优先指向手写定义处。
- 仓内已有 `docs/biz/interface/` 等既有资产文档时，可作为术语线索来源，但释义与映射仍以代码为最终依据。

### 第 2 步：子域划分（从代码功能域派生）

子域划分与 biz-interface-analyze 的功能域归类口径一致（按优先级：路由路径前缀 → controller/service 归属 → IDL service 分组 → 业务语义相近）：

- 仓内已产出 `docs/biz/interface/` 接口资产 → 直接复用其功能域划分作为词典子域。
- 未产出 → 按上述口径从代码自行归纳功能域作为词典子域；禁止按技术层划分子域（如"controller 层词汇"）。

每个术语归入一个主属子域；跨子域共用、不属于任何单一功能域的术语（如通用状态、通用错误码）归入固定的「通用」节。

### 第 3 步：术语归集（五类来源）

按以下五类来源全仓归集术语候选，语言无关、按仓内实际形态取舍：

1. **对外接口文档 / 请求响应模型**：接口契约（proto / thrift / OpenAPI）、请求与响应 struct 的字段名及注释——字段名是术语候选，注释是释义候选。
2. **DB 实体注释**：ORM model / 表结构定义、字段注释、建表 SQL 注释。
3. **事件模型**：消息 topic、事件 struct、事件类型枚举。
4. **错误码定义**：错误码常量 / 枚举及其注释——每个业务错误码是一个术语（业务异常概念）。
5. **常量定义**：状态枚举、类型常量、业务开关常量（如 `StatusNormal` / `StatusFrozen`）。

每个术语候选记录五样：候选词（中文/英文）、**术语类型**（由来源确定，映射见第 5 步类型表：来源 1/2 → 实体与业务概念、来源 3 → 事件、来源 4 → 错误码、来源 5 → 常量与状态枚举）、代码标识符、来源文件路径（不带行号）、上下文注释。五类来源全部排查，某类确实没有时在成品「说明」节注明"本仓无 XX 来源"，证明排查过。

### 第 4 步：词条加工

对每个术语候选加工成词条，四列齐全：

- **术语**：业务通用名（优先采用代码注释/既有文档中的中文业务名；代码只有英文标识时以英文标识为术语名）。
- **释义**：必须有代码依据（注释 / 字段名 / 枚举值）。代码只能支撑部分含义时，只写代码能支撑的部分；代码未体现的业务含义标注"代码未体现，待确认"，禁止脑补。
- **语境边界**：同名异义时逐语境一条（同一词在不同子域/不同结构中含义不同，各写一条并注明适用语境）；单义术语该列写"-"。
- **代码命名映射**：代码标识符（struct 名 / 字段名 / 常量名 / 枚举值）+ 文件路径（不带行号）；一个术语多处映射逐条列出。

**同义异名合并**：不同名字指同一业务概念（如 IMEI / 设备标识）合并为一条，条内互指（"同义：IMEI"），禁止一词多条。

### 第 5 步：产出主文档 + 子域文档并落盘 docs/biz/lexicon/

- **文件布局**（全仓一套，落盘被分析仓根目录 `docs/biz/lexicon/`）：
  - 主文档 `lexicon.md`（文件名固定）：元信息 + 说明（词汇口径、拆分口径、五类来源排查结论、同义合并原则）+ 待确认清单（**全仓汇总**，跨子域一处跟进）+ 子域导航表（子域名/词条数/子文档链接）+ 「通用」节词条（同四类分组）。
  - 子域文档 `lexicon-{子域锚点}.md`：每功能域 1 篇，只含该域四类术语类型小节的词条表；篇内不重复元信息/说明/待确认清单，以回链指向主文档。
  - 不产 README（主文档 `lexicon.md` 即身份；域索引 `docs/biz/README.md` 与总索引由 all-index 统一生成，本 skill 不维护）。
- **模板**：主文档按 references/lexicon-template.md 填充；子域文档按 references/lexicon-subdomain-template.md 填充。
- **子域文档内组织规则**：按四类术语类型分小节，固定顺序为 实体与业务概念 → 常量与状态枚举 → 错误码 → 事件；无某类术语时省略该类型小节（不写"无"）；同一术语只落一个类型小节（以其来源类型为准，不重复罗列）。
- **命名口径**：子域锚点取功能域代表性代码标识符转 kebab-case，与 docs/biz/interface/ 子文档锚点保持一致（如 interface-login.md ↔ lexicon-login.md），禁止 AI 自由起名。
- 同名文件已存在**直接覆盖更新**——词典是活文档，固定名、覆盖更新，git diff 即演进史；重跑时逐子域文档、按类型逐组对比刷新（术语下线则从表中移除，释义演进则更新释义；**子域整体下线则删除对应子域文档**，并同步刷新主文档导航表与待确认清单，目录内不留游离 lexicon-*.md）。

### 第 6 步：输出后自检（防漏、防臆造）

交付前执行自检：

1. **来源覆盖**：五类来源逐类确认排查过（含"确实没有"的类目，已在主文档「说明」节注明）。
2. **类型归属**：每条术语的类型小节归属与其来源类型一致（来源→类型映射全部落位）；同一术语未在多个类型小节重复出现。
3. **映射反查**：抽样 grep 核实词条的代码命名映射——标识符必须真实存在于所引文件路径，核实不通过的词条修正或删除。
4. **待确认闭环**：所有标注"代码未体现，待确认"的释义汇总进主文档「待确认清单」节，禁止散落在各子域文档表格里无人跟进。
5. **子域口径**：词典子域与第 2 步的功能域划分一一对应（外加主文档「通用」节），无技术层命名的子域。
6. **导航闭环**：主文档子域导航表与目录内 `lexicon-*.md` 一一对应——导航所列子域文档全部存在、链接正确；目录内无导航之外的游离子域文档（含已下线子域的残留文件）。
7. **拆分完整性**：每条术语归属且仅归属一篇文档（某个子域文档，或主文档「通用」节），无跨文档重复罗列。

## 输出模板

主文档严格按 references/lexicon-template.md 骨架填充，子域文档严格按 references/lexicon-subdomain-template.md 骨架填充——只填占位符与表格行；写作规则见上文各步骤与「关键约束」。

## 关键约束

- **语言无关**：不预设被分析仓的语言/框架，按第 1 步实际探测结果走，禁止凭仓库名或已知项目结构臆测。
- **基于实证**：所有词条必须有代码支撑，证据形式为文件路径，**不带行号**（行号随代码变更失效且无跨工具稳定性）；"代码命名映射"列同样只写文件路径。
- **释义必须有代码依据**：释义只能写代码注释 / 字段名 / 枚举值能支撑的内容；代码未体现的业务含义标注"代码未体现，待确认"并汇总进待确认清单，禁止脑补业务含义。
- **命名从代码派生**：主文档文件名固定 `lexicon.md`，子域文档固定 `lexicon-{子域锚点}.md`；子域从代码功能域派生（与 biz-interface-analyze 口径一致），子域锚点取功能域代表性代码标识符转 kebab-case、与 interface 子文档锚点一致，禁止 AI 自由起名——保证重跑产出口径稳定、资产不断代。
- **活文档覆盖更新**：主文档与各子域文档同名直接覆盖，不保留历史副本、不加日期后缀；子域下线时删除其文档并同步主文档导航表。
- **只读不改**：只读、只分析、只产出文档，不改动被分析代码仓的任何文件（新建 `docs/biz/lexicon/` 目录与文档文件除外）。
- **成品纯净**：最终文档只含成品内容（元信息、说明、待确认清单、词条表）。第 3 步的归集清单、grep 命中输出等探测过程产物仅供自检，绝不写入最终文档——其结论以文件路径证据形式进入词条表。
- **同义合并、异义分条**：同义异名合并为一条并互指；同名异义按语境逐条列出，语境边界列不得留空糊弄。
- **不维护索引**：本 skill 不产出域索引与总索引——`docs/biz/README.md` 与 `docs/README.md` 由 all-index skill 统一生成。
- **文档语言**：输出文档用中文，技术术语（struct / enum / topic / RPC 等）与代码标识符保留英文。
