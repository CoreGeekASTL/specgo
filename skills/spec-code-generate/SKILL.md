# spec-code-generate — 代码生成执行

依据 story 设计文档与 develop-task 施工单（单文档多 Task），落地**完整、可运行、零 TODO** 的代码。

**交互双模式（全局条款）**：本 skill 所有询问点**默认使用 ask-human 工具**；若任务开始时用户声明"以报告形式呈现"（或同类意思），则全程**不使用 ask-human**——所有待澄清/待审视内容以报告形式输出，等用户回复后继续。

## 角色分工（先记牢）

| 角色 | 职责 |
|---|---|
| 测试子代理 | **只写自测用例**：以 develop-task 全部 Task 的完整契约 + 行为对照表 + 测试清单为唯一依据一次写完全部测试（TDD 视角，禁止看实现代码）；定点核实仓内测试框架约定与存量测试样板；不跑测试 |
| 实现子代理 | **只写实现代码**：读输入文档、核实存量代码、将全部 Task 的修改文件清单逐文件落地（清单外不改）；可多个并行（跨 Task 按文件分组）；禁止看测试文件；不跑验证 |
| 主代理 | 一次性派发两线子代理；两线全部完成后**全量测试**（单测/集成测试/验证命令）；失败**归因**（以 develop-task 契约与行为对照表为裁判，判定测试错还是实现错）并**全权修正**（测试与实现都可改）；零 TODO 复核；组织审视门；推进后续流程 |

## 两条铁律（不可协商）

### 铁律一：完整代码，零 TODO

- 交付的每一个文件都必须是完整实现——函数体、分支、错误处理、边界条件全部写实。
- **禁止任何形式的占位**：`TODO`、`FIXME`、`// 待实现`、`// ...省略...`、`throw new Error("not implemented")`、`pass  # TODO` 等一律不允许出现。
- 自检：交付前全量搜索改动文件中的 `TODO|FIXME|XXX|HACK|待实现|省略|not implemented`，命中即返工。
- 写不出完整实现 = 输入不足（需求未明确/设计缺要素/存量代码事实不清），此时返回**待确认清单**结束本轮，由主代理向用户澄清后回传续做——**绝不**用 TODO 先糊弄过去。

### 铁律二：两线一次性派发，主代理全量测试与修正

- **两线并行、一次派完**：主代理一次性派发——1 个测试子代理（一次写完全部 Task 的测试）+ N 个实现子代理（跨全部 Task 按文件分组，一次实现全部代码）。两线的**唯一共同基准是 develop-task**（完整契约 + 行为对照表）：测试子代理禁止读实现产出，实现子代理禁止读测试文件，各自独立从文档出发。
- **子代理的职责边界到"产出写完"为止**——测试执行、失败归因与修正、验证命令、审视门全部由主代理承担。
- **实现线分组**：修改文件清单按互不依赖的文件组拆分，无依赖的组**同一条消息并行派发**多个实现子代理（每组一个子代理，prompt 只带该组文件所需的文档与代码上下文）；组间有依赖（如接口定义先于调用方、基础 Task 的公共结构先于使用方）严格串行——依赖关系以 develop-task「任务拆分总览」与各 Task 修改文件清单的依赖前置为准。
- **测试与实现同标准**：完整断言、禁止空用例占位。

## 子代理执行纪律

### 测试子代理（三步）

1. **加载输入（只读）**：develop-task 全部 Task 章（完整契约 + 行为对照表 + 测试清单）+ story 相关要素节 + 两文档显式引用的仓内文档；**禁止读实现子代理的产出文件**（实现代码一律不看）。
2. **定点核实存量测试约定**：只读仓内既有测试文件确认测试框架、命名与断言风格样板；其余代码一律不读。
3. **按契约写测试**：行为对照表逐场景对应至少一个用例（含"不变"场景的回归断言）；测试清单逐条落地并标注看护改动；设计文档未明确的预期行为返回待确认清单，不脑补。

### 实现子代理（三步）

1. **加载输入文档（只读三波）**：story 设计文档（全读）+ develop-task（修改文件清单=编码唯一任务来源，验证方式=验收依据）+ 两文档**显式引用**的仓内文档；未引用的一律不读，禁止列目录找文档；**禁止读测试文件**。
2. **定点核实存量代码**：只读本组"修改"类文件的改动点上下文（函数级）；"新增"类读文档指明的复用样板；其余代码一律不读。
3. **按清单实现**：本组修改文件清单逐文件落地，清单外不改；设计文档与存量代码冲突时以代码为准并列出偏差；需求未明确处返回待确认清单，不脑补。

### 子代理返回格式

生成/修改文件清单 + 冲突偏差 + 待确认清单（如有）。

## 主代理测试与验收纪律（五步）

两线子代理全部完成后，主代理统一执行：

1. **组装**：合并测试子代理与各实现子代理产出，复核零 TODO 自检（实跑搜索命令，命中数必须为 0）。
2. **全量单元测试**：实跑仓内单测命令，覆盖全部 Task 的新增/改动逻辑（结果到测试函数级：逐函数 PASS/FAIL）。
3. **失败归因与全权修正**：测试失败时对照 develop-task 行为对照表逐场景判定——实现不符合对照表**改实现**；测试与契约/对照表不符**改测试**；两边都与文档一致但仍失败=文档缺陷，返回待确认清单交用户澄清。修正由主代理直接完成，修正后重跑直至全绿；禁止为凑绿而两边各改一点迁就过关。
4. **集成测试**：代码仓存在集成/E2E 测试约定时（仓内测试目录，或 README/AGENTS.md 声明的集成测试方式）**必须主动运行**，不等用户提醒（结果到用例步骤级）；不存在则跳过并注明。
5. **全量验证**：运行 develop-task 所有 Task「验证方式」小节的命令（构建/测试）与整体构建，失败归因修正后重跑；未跑过验证命令不得宣称完成。

## 交付摘要（主代理汇总交付）

生成/修改文件清单 + 冲突偏差 + 零 TODO 自检结果（搜索命令与命中数=0）+ 验证命令结果（DT 到测试函数级：逐函数 PASS/FAIL）+ 失败归因与修正记录（修正了哪些测试/实现、依据哪条对照表）+ 集成测试结果（到用例步骤级：逐步骤结果与环境前置）+ **实际加载的文档清单**（各子代理返回合并：story/develop-task/显式引用的仓内文档，逐条带路径）。

交付摘要呈现后按交互双模式完成用户审视：**默认**用 ask-human 询问是否审视通过（有意见由主代理整改后重新呈现）；**报告模式**仅输出交付摘要。

## 红线

| 想法 | 现实 |
|---|---|
| "这里先 TODO，回头补" | 零 TODO 是交付红线——写不出完整实现就返回待确认清单 |
| "测试让实现子代理顺手写了" | 测试与实现分线并行——测试子代理从契约独立写，禁止看实现 |
| "测试和实现对不上，互相改改凑绿" | 以 develop-task 契约与行为对照表为唯一裁判，主代理归因后单边修正 |
| "让子代理把测试也跑了省事" | 子代理只产出；测试执行、归因与修正是主代理职责 |
| "文件多，一个子代理全包了" | 实现线按文件分组并行派发，不硬塞单个上下文 |
| "测试写个空用例占位" | 测试与实现同标准——完整断言，禁止占位 |
| "集成测试等用户提醒再跑" | 仓里有集成/E2E 测试主代理就必须主动运行 |
| "代码写完就算完成" | 全部验证命令实跑通过才算完成 |
