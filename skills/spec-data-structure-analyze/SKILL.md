# 代码仓关键数据结构分析

从存量代码仓出发，识别承载关键业务与特殊语义的数据结构，按**用途**分组产出**一个主文档 + 多个子文档**，归档到 `docs/business/data-structure/`，回答"这个仓靠哪些数据结构撑起核心流程、各自承担什么作用"。

> 注意：本 skill 的"关键数据结构"= 仓内承载核心业务状态/流程、或自定义实现、或高被引用、或有特殊并发/性能语义的数据结构。**不是**把仓里每一个 `[]byte`、`map[string]string` 都列出来——那是无信息量的流水账。语言原生的普通容器只有在"承担关键作用"时才收录。

分析遵循五步工作流：

1. 明确范围与排除目录
2. 扫描数据结构使用点（grep 模式 + 自定义结构识别）
3. 关键性判定与按用途分组
4. 产出主文档 + 各用途子文档
5. 输出后自检（防漏实例、防臆造）

## 第 1 步：明确范围与排除目录

- 确认代码仓路径、主要语言（Go/Java/Python/C++ 等），据此选取对应的容器语法作为探测模式。
- 确认排除目录：默认排除 `vendor/` `node_modules/` `third_party/` `*_gen/` `*.pb.go` 生成代码；测试目录**默认纳入**（测试中的关键 mock/夹具结构也列出，标注"仅测试"）。
- 确认分析深度：用户未说明时默认按"资产级"执行，面向资产沉淀（核心作用与使用模式说明），而非清单级流水账。

## 第 2 步：扫描数据结构使用点

两条线并行，再交叉核对：

1. **语言原生容器**：按仓内语言用 grep 扫描容器使用模式，详见 [references/data-structure-catalog.md](references/data-structure-catalog.md) 的探测线索。典型模式（Go 示例，其它语言见 catalog）：
   - 切片/列表：`\[\][A-Z]`、`make\(\[\]`
   - map：`map\[[A-Z]`、`make\(map`
   - 集合（map 当 set 用）：`map\[.*\]struct\{\}`、`map\[.*\]bool`
   - 链表/队列/栈：`container/list`、`list.New`、`chan `、自定义 `type Xxx struct { next *Xxx }`
   - 数组（定长）：`\[[0-9]+\][A-Z]`
   - 自定义容器：`type Xxx struct` 中字段为 `map/slice/chan` 且带锁、或命名含 cache/pool/queue/ring/buffer/registry
2. **自定义结构**：用 grep 找命名特征——`cache`、`pool`、`queue`、`ring`、`buffer`、`registry`、`index`、`table`、`bucket`、`node`，命中后精读定义文件，判定是否为自定义容器（自实现增删改查/并发控制）。
3. **查漏**：对照 catalog 的类型清单逐项核对——仓内有但扫描没命中（如宏/表驱动注册、自封装容器类、泛型容器）的必须追查；注意"易遗漏项"（map 当集合用、channel 当队列用、sync.Map、带锁的 map 字段、泛型容器、自实现 LRU/环形缓冲）。

扫描结果记录中间清单（实例标识 = 类型 + 定义位置），供第 5 步差集自检用。

## 第 3 步：关键性判定与按用途分组

逐候选判定是否"关键"，**至少满足一条**：

1. 承载核心业务状态/流程数据（缓存表、任务队列、连接池、注册表、会话上下文）
2. 自定义实现（非语言原生，如手写 LRU/环形缓冲/跳表/并发安全 map）
3. 高被引用（被 ≥N 个模块读写，N 按仓规模定，默认 3；channel/全局 map 重点关注）
4. 有特殊并发/性能语义（并发安全容器、无锁队列、sync.Pool、双缓冲）
5. 是某功能域的数据中枢（其他逻辑围绕它读写）

规则：

- **不臆造关键性**：拿不准的宁可不收；未入选的候选在回复中简要说明原因（不写入文档），供人工复核。禁止"这是个 map 所以收"式收录。
- **数量控制**：关键数据结构贵在精不在多，单仓建议 10~40 个实例、3~10 个用途；用途超出说明分组过细，合并相近用途；实例超出说明筛选过宽，回到判定标准收紧。
- **区分"语言原生容器的关键用法"与"自定义容器"**：原生容器只在承担关键作用时收录，且在子文档里注明"原生切片，关键用法"；自定义容器单列。
- 每个入选结论有代码证据（定义位置、读写点），接口与唯一实现合并为一个条目。

按用途分组：将入选实例按**业务用途**聚类（如会话缓存、路由注册表、白名单集合、任务队列、连接池、配置缓存），同一用途下的实例可以跨越多种数据结构类型（map/slice/自定义容器不限）。**用途名用英文 kebab-case**（如 `session-cache`、`route-table`），用于子文档文件名；仓内未出现的常见用途不建空文档。数据结构类型只作为探测与描述维度（见 [references/data-structure-catalog.md](references/data-structure-catalog.md)），不作为分组维度。

## 第 4 步：产出主文档 + 各用途子文档

产出结构如下，归档到 `docs/business/data-structure/`：

```
<repo>/docs/business/data-structure/
├── README.md                                   # 主文档：元信息 + 用途索引导航表
├── spec-data-structure-<用途1>.md               # 子文档：核心作用 + 关键实例表 + 实例详解 + 使用模式
├── spec-data-structure-<用途2>.md
└── ...
```

**命名规则**：
- 主文档：`README.md`（目录索引惯例，不以 `spec-` 开头）
- 子文档：`spec-data-structure-<用途名>.md`，用途名英文 kebab-case（如 `spec-data-structure-session-cache.md`）
- 子文档必须 `spec-` 开头，统一放 `docs/business/data-structure/`

两套模板：主文档按 [references/readme-template.md](references/readme-template.md) 填充（固定三行元信息表：分支/更新日期/Skill + 用途索引表，每行含用途/实例数/核心作用/子文档链接，无死链）；README 只起导航作用，不加其他章节。

子文档按 [references/subdoc-template.md](references/subdoc-template.md) 填充，四节——① **核心作用**（该用途数据结构在仓内承担的核心作用与业务价值，2~4 句）② **关键实例表格**（实例名/作用/定义位置，**定义位置只带文件路径不带行号**）③ **实例详解**（结构定义概要、关键字段/约束、典型操作、使用点 `文件:行号`、并发/性能语义）④ **使用模式与约定**（仓内既有的封装与使用约定，附证据）。

**人类友好硬性要求**：

- 每个用途一个子文档，**按业务用途命名**，禁止按技术层命名（如"controller 层的数据结构"），也禁止按数据结构类型命名（如"map"）。
- 关键实例必须用**表格**列出（实例名/作用/定义位置），禁止散文段落描述单个实例。
- **"定义位置"列只填文件路径，不带行号**（如 `models/cache.go`）；使用点、并发控制点等需精确定位的证据锚点保留 `文件:行号` 格式。
- 每个实例的详细说明（结构定义、使用点、并发模型）**写在实例表格下方**，逐个实例说明，不要把所有实例堆成一张孤立的大表。
- 只列"理解该实例必须知道"的字段与约束，超过 8 字段只列关键，不整段搬运 struct 定义。
- 主文档用途索引表每行带子文档链接，可从总览直跳详情；子文档元信息带返回主文档链接。
- 单用途实例数 > 10 时，列代表性 5~10 处并注明"全量见 xxx"，禁止全量罗列刷屏。

**更新策略**：`docs/business/data-structure/` 下文档已存在时按用途逐篇对比更新（实例被移除则删行、作用漂移则改行；用途已无实例则标注"已下线"并归档或从索引移除），不要整目录覆盖重写；主文档索引随用途增删同步更新。

## 第 5 步：输出后自检（防漏实例、防臆造）

文档产出后、交付前必须执行差集自检。漏实例的根因通常是"扫描到了但归类时丢了"，靠通读复查很难发现，必须用清单比对：

1. **生成全量清单 A**：从第 2 步扫描结果提取全部关键实例标识（用途 + 定义位置，如 `session-cache · models/session.go`）。
2. **生成已记录清单 B**：从已产出的各子文档实例表格提取全部实例标识。
3. **差集比对**：
   - **A − B（漏记）**：逐个处理——补入对应用途子文档；无法归入任何用途的在回复中说明理由。禁止静默丢弃。
   - **B − A（多出）**：逐条核实——是扫描盲区（自定义容器命名不在模式库内、宏展开）则补入扫描清单并保留且注明依据，是臆造则删除。
4. **自检结论写入 README**：在用途索引表后加一行自检结论，格式：`自检：扫描 N 个实例，已记录 N 个，差集已清零（YYYY-MM-DD）`。差集未清零的禁止交付。

## 第 6 步：验证 mermaid 图可渲染（收尾必做）

产出文档中含 ```mermaid 代码块（数据结构全景图、类型关系图等），交付前必须运行 spec-mermaid-diagram skill 的本地验证脚本逐文件校验：

```bash
node <specgo插件目录>/skills/spec-mermaid-diagram/scripts/validate-mermaid.mjs <产出文件...>
```

- 全部 VALID 才算完成；INVALID 按报错行号定位修复后重验，禁止跳过。
- 首次使用需先在脚本目录执行 `npm install`（安装 mermaid + linkedom，node_modules 不入库）。
- 画图规则（label 一律加引号、时序图消息禁 `;`、裸 `end` 禁用等）见 spec-mermaid-diagram skill 的「语法红线」。

## 质量检查清单

交付前逐项确认：

- [ ] 容器类型清单全部排查过（catalog 逐项核对，未命中的类型确认"确实没有"）
- [ ] **已执行第 5 步差集自检：扫描清单与文档清单差集清零**
- [ ] README 开头为固定三行元信息表（分支/更新日期/Skill）
- [ ] README 含自检结论行（扫描数/已记录数/差集清零日期）
- [ ] README 含用途索引表（含子文档链接，无死链）
- [ ] 产出 1 个主文档 `README.md` + N 个子文档 `spec-data-structure-<用途名>.md`，归档在 `docs/business/data-structure/`
- [ ] 每个子文档含：核心作用 / **关键实例表格** / **表下逐实例详解** / 使用模式与约定 + 返回主文档链接
- [ ] 关键实例表格列含 实例名 / 作用 / 定义位置，无段落式散文
- [ ] **"定义位置"列只填文件路径，不带行号**；使用点等证据锚点保留 `文件:行号`
- [ ] 每个实例的详细说明写在实例表格下方逐个说明
- [ ] 只列关键字段与约束，未整段搬运 struct 定义
- [ ] 子文档按业务用途命名（kebab-case），无技术层命名、无数据结构类型命名
- [ ] 子文档文件名符合 `spec-data-structure-<用途名>.md`
- [ ] 一次性局部变量 / 生成代码 / 测试代码未被误收为关键数据结构
