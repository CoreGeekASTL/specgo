# 框架用法分析维度

用于第 4 步「用法模式分析」：对每个识别出的框架，沿八个维度提取用法。所有结论必须有代码证据（文件路径，不带行号），禁止臆测。

## 八个分析维度

### 1. 用途定位
该框架在系统中承担什么角色？用在哪些模块、解决什么问题？（例：gRPC 仅用于服务间北向接口，内部模块间用自研消息总线。）

### 2. 初始化与配置
- 在哪初始化（main/单例/启动类/全局变量）？
- 配置项从哪来（配置文件/配置中心/硬编码）？关键配置项及实际取值（线程数、超时、队列长度、地址）。
- 生命周期：何时创建、是否复用、如何关闭（有无泄漏迹象）。

### 3. 核心使用模式
提取 1-3 个典型调用序列作为"用法骨架"，附真实代码片段（注明来源文件路径，不带行号）。例：
- RPC 服务端：IDL → 生成 stub → 实现 handler → 注册到 server → 启动监听
- 线程池：提交任务 → 回调/ future 取结果 → 池关闭
骨架要让读者看完就知道"新代码照这个写"。

### 4. 封装层与扩展点
存量代码是否对框架做了封装（Wrapper/Facade/Base 类/拦截器/中间件）？
- 判定线索：框架原生 API 只出现在少数文件，业务代码大量调用的是另一套自有 API。
- **封装层是用法分析的第一优先级**：新业务代码几乎总是应该用封装层而非裸 API。写清封装层入口（包路径/头文件）、它隐藏了什么、暴露了哪些扩展点。

### 5. 并发与线程模型
- 调用发生在哪个线程/协程上下文？回调在哪个线程执行？
- 线程亲和性约束（如某 Actor 串行处理、某回调禁止阻塞）。
- 共享状态如何保护（锁/无锁/串行化 executor）。

### 6. 错误处理与容错
- 错误如何表达（异常/错误码/status 对象）？存量代码怎么处理（吞掉/上抛/转换）？
- 超时、重试、熔断的实际配置与位置。
- 不一致点：同一框架在不同模块错误处理风格不同，要列出。

### 7. 约定与规范
从代码事实归纳（不是从文档抄）：
- 命名约定（XxxServiceImpl、*Actor、*Worker）
- 放置位置（handler 放哪层目录、IDL 放哪）
- 禁止事项的实际证据（如无人直接 new 池，全走工厂）

### 8. 已知问题与反模式
存量代码中的坏味道，新代码要避免：
- 绕开封装层直用裸 API 的个例
- 资源未释放、超时缺失、线程池无界队列
- 同一能力两套实现并存

## 分析深度分级

按第 1 步确认的分析目的选择深度：

| 深度 | 适用目的 | 每框架投入 |
| --- | --- | --- |
| 浅（清单级） | 技术栈盘点、汇报 | 维度 1 + 使用广度统计 |
| 中（模式级） | 架构文档、新人上手 | 维度 1-4，骨架级代码片段 |
| 深（资产级） | AI 代码生成、重构迁移 | 全 8 维度，含真实片段与文件引用 |

## 抽样策略

调用点成百上千时禁止全量读：
1. 从扫描输出的热点文件取 Top 3-5（代表最常见用法）。
2. 再取 1-2 个调用链最复杂的使用点（代表高级用法）。
3. 封装层文件全读（量小且价值最高）。
4. 发现模式分叉（两种以上并存用法）时，每支各取 1 例。
